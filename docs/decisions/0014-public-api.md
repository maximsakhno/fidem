# 0014. Публичный API пакета

- Статус: реализовано
- Дата: 2026-11-27
- PR: #22
- Связано: 0004 (мидлвари эффектов), 0008 (транзакции БД и atomic-команды), 0009 (запросы и транзакции как эффекты), 0012 (сериализация); README → «Архитектура», «Транзакции», «DI»

## Контекст

Пользователь импортировал всё из модулей реализации: `fidem.operation_engine`, `fidem.environment`, `fidem.di.effects`. Поэтому любой модуль, который он задевал, становился частью контракта, и перестроить модули без поломки пользователя было нельзя. Ошибки пакета наследовали `Exception` напрямую, и поймать все ошибки фреймворка одним `except` было нельзя. Оба места нашлись при рефакторинге по правилам чистого кода.

## Цель и границы

- Входит: что импортируется из корня пакета, корневая ошибка, неявная транзакция как обычная транзакция.
- Не входит: переименование `EnvironmentImpl` и судьба абстрактного `Environment`.

## Решение

- **Публичный API импортируется из корня:** `from fidem import Command, EnvironmentImpl`. Модули реализации можно перестраивать: корень сохраняет имена. Импорт из модулей по-прежнему работает.
- **Драйверы и сериализаторы на сторонних библиотеках — не в корне,** а в своих модулях: `fidem.asyncpg`, `fidem.pydantic`, `fidem.msgspec`. Поэтому `import fidem` не требует extras.
- **Механика ядра — не в корне:** инструкции движка, контейнеры DI и гардов, ключи встроенных зависимостей, эффект записи в outbox, помощники `fidem.testing`. Это внутреннее устройство и инструменты для авторов драйверов, а не API приложения.
- **Все ошибки fidem наследуют `fidem.Error`,** поэтому любую ошибку фреймворка можно поймать одним `except`, а конкретную — по её типу.
- **`ValueError` и `TypeError` из fidem означают ошибку в самом fidem,** а не в коде пользователя: свои ошибки пользователю fidem бросает только наследниками `fidem.Error`.

## Развилки

### Абстрактный `Environment` с единственной реализацией `EnvironmentImpl`

- Выбрано: оставить абстрактный класс и имя `EnvironmentImpl`.
- Почему: окружений может быть несколько, например тестовое (README → «Архитектура»).
- Отвергнуто: убрать абстрактный класс и переименовать `EnvironmentImpl` в `Environment` — по правилам чистого кода интерфейс с одной реализацией лишний, но второе окружение уже заложено в концепт.

### Неявная транзакция

- Выбрано: эффект БД вне явной транзакции движок выполняет так, будто effectful-функция вызвала транзакцию из одного этого эффекта. Для этого есть две обычные транзакции — неявная читающая и неявная пишущая. Контекст транзакции хранит только транзакцию, признак «только чтение» берётся из неё. Это пересмотр 0008 и 0009: там неявную транзакцию открывал Environment, а объекта у неё не было.
- Почему: в контексте с отдельным признаком «только чтение» рядом с транзакцией можно было записать противоречие — «только чтение» и пишущую транзакцию. Неявная транзакция сводится к уже существующему пути явных транзакций, и отдельный код для неё в Environment не нужен. Движок решает все транзакции, поэтому в durable-режиме запись эффекта и запись журнала можно делать одной транзакцией (0008).
- Цена: мидлвари эффекта БД работают внутри его транзакции, и ретрай мидлварью эффекта повторяет вызов в той же транзакции. В PostgreSQL после ошибки она сломана, поэтому ретраить приходится операцию — так же, как внутри явной транзакции. Мидлварь с паузой между попытками держит транзакцию открытой. Это пересмотр 0004, где каждый ретрай получал новую транзакцию.
- Отвергнуто:
  - проверять противоречие в конструкторе контекста — противоречие по-прежнему можно записать, оно лишь ловится при создании;
  - отдельный тип неявной транзакции, который создаёт движок, а открывает Environment, — ретраи сохраняются, но появляются новый тип, поле в инструкции и отдельная ветка в Environment.

### Одиночное чтение без транзакции БД

- Выбрано: драйвер находит настройки неявной читающей транзакции по её объекту, как у любой транзакции. У asyncpg по умолчанию это read committed, а при read committed читающая транзакция транзакцию БД не открывает.
- Почему: раньше драйвер узнавал одиночное чтение по отсутствию объекта транзакции (0009). Теперь объект есть всегда, а существующий механизм настроек по транзакции закрывает этот случай без особой ветки.

## Сочетание с другими фичами

- Новое публичное имя добавляется в корень пакета, иначе пользователь импортирует его из модуля и снова привязывается к устройству пакета.
- Новая ошибка, которую видит пользователь, наследует `fidem.Error`.
- Новый драйвер на сторонней библиотеке живёт в своём модуле и в корень не попадает.
