# 0002. DI для обработчиков эффектов

- Статус: реализовано
- Пересмотрено: 0006 (одна форма фабрики)
- Дата: 2026-11-22
- PR: #5
- Связано: 0001 (начальный концепт); README → «DI»

## Контекст

По концепту у обработчиков нет фиксированной сигнатуры, а зависимости подставляются автоматически. До этого PR обработчик эффекта получал только контекст и сам эффект, и брать подключения к БД, клиенты, транзакции ему было неоткуда. У таких зависимостей разное время жизни, а некоторые надо корректно закрывать.

## Цель и границы

- DI для обработчиков эффектов: связывание, фабрики, время жизни зависимостей, проверка графа.
- Не входят: DI для обработчиков сообщений, синхронные фабрики и классы как фабрики, вспомогательные конструкторы для регистрации зависимостей.

## Решение

- **Всё — зависимости.** Каждый параметр обработчика или фабрики — зависимость, связывание автоматическое, без явных маркеров. Сам эффект, сообщение и их контексты — тоже зависимости и подчиняются общим правилам, без особых случаев.
- **Сопоставление: сначала тип, потом имя.** Кандидаты — зависимости, тип которых совпадает с типом параметра или наследует его. Один кандидат — берём его. Несколько — выбираем по имени параметра. Иначе ошибка: зависимость не найдена или выбор неоднозначен.
- **Всё готовится заранее.** При создании Environment граф зависимостей строится и проверяется целиком, включая зависимости, которые пока никому не нужны: всем параметрам хватает зависимостей, выбор однозначен, циклов нет, время жизни соблюдено. Для каждого обработчика заранее готовится порядок создания зависимостей, и во время обработки ничего не выясняется — подготовленные шаги просто выполняются.
- **Создание зависимостей отделено от вызова обработчика,** чтобы стратегию создания можно было менять, не трогая вызов.
- **Фабрики** различаются тем, кто отвечает за жизненный цикл: готовый объект — никто; функция — создаёт сама, закрывать не нужно; генератор — создаёт до `yield` и закрывает после. Генератор получает ошибку, с которой завершилась обработка, и может, например, откатить транзакцию вместо коммита.
- **Время жизни:** приложение, сообщение, эффект. Зависимость может зависеть только от зависимостей с таким же или более долгим временем жизни.
- **Environment получил жизненный цикл:** запуск и остановка, вызов вне них — ошибка. На старте создаются, на остановке закрываются зависимости приложения.

## Развилки

### Учитывать ли наследование при сопоставлении

- Выбрано: учитывать. Параметр с базовым типом получает зависимость любого наследника.
- Почему: обработчик просит абстракцию (базу данных), а фабрика возвращает конкретную реализацию. Так же фабрика может получить эффект по базовому классу и работать с любым эффектом.
- Отвергнуто: только точное совпадение типа — фабрике пришлось бы объявлять абстрактный тип вместо реального.

### Приоритет точного совпадения типа

- Выбрано: приоритета нет. Если подходят и сам тип, и наследник, выбор делается по имени, иначе ошибка.
- Почему: явное лучше неявного. Неявное правило выбора легко не заметить, а имя однозначно.

### Когда создавать зависимости приложения

- Выбрано: сразу на старте, все, включая неиспользуемые, параллельно по графу: каждая — как только готовы те, от которых она зависит. Закрываются так же параллельно, по графу в обратную сторону.
- Почему: ошибки конфигурации и подключения видны сразу на старте, а не на первом запросе. Неиспользуемые зависимости могут понадобиться позже, а их создание может иметь смысл само по себе, например проверку подключения. Параллельность ускоряет старт.
- Отвергнуто: ленивое создание.

### Зависимости сообщения и эффекта

- Выбрано: зависимости сообщения создаются лениво, при первом эффекте, которому нужны; зависимости эффекта — перед вызовом обработчика. И те и другие — последовательно.
- Почему: какие эффекты выдаст обработчик сообщения, заранее неизвестно, поэтому создавать всё на старте сообщения расточительно. Последовательно — потому что задача asyncio на каждую зависимость каждого эффекта ощутимо снизила бы производительность.

### Ошибка закрытия зависимости эффекта

- Выбрано: эффект считается упавшим, ошибка уходит в обработчик сообщения как ошибка эффекта.
- Почему: закрытие может быть содержательной частью эффекта, например коммитом транзакции. Если коммит не прошёл, эффект не выполнен.
- Отвергнуто: засчитать результат, а ошибку закрытия только залогировать.

## Нюансы

- Сообщение — тоже эффект, поэтому параметр с базовым типом эффекта получал бы и эффект, и сообщение, и выбор был бы неоднозначным. Поэтому сообщение подходит только параметрам с типом сообщения. Какое именно сообщение породит эффект, заранее неизвестно, поэтому конкретный тип сообщения проверяется в рантайме.
- Готовый объект можно зарегистрировать только на время жизни приложения: создавать и закрывать его некому.
- При ошибке закрываются все уже созданные зависимости, даже если какая-то из них сама падает при закрытии.
- Отмена и прерывание не смешиваются с ошибками закрытия в одну группу ошибок: иначе asyncio не распознал бы отмену.

## Сочетание с другими фичами

- DI для обработчиков сообщений: фабрики будут effectful-функциями, а правила сопоставления и проверки графа — те же.
- Параллельный запуск эффектов: два эффекта смогут одновременно создавать одну и ту же зависимость сообщения. Пока эффекты выполняются последовательно, это не учитывается.

## Открытое

- Выбор между последовательным и параллельным созданием зависимостей сообщения и эффекта.
- Одновременный запуск Environment и вызовы во время остановки не защищены.
- Вспомогательные конструкторы для регистрации зависимостей.
