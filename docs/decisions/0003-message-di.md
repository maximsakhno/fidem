- Дата: 2026-11-22

## Контекст

DI для обработчиков эффектов уже был (0002), а обработчик сообщения по-прежнему получал только контекст и сообщение. По концепту фабрики зависимостей сообщений — effectful-функции: зависимость возвращается через управляющий эффект, а код после него закрывает зависимость.

## Цель и границы

- DI для обработчиков сообщений: свободная сигнатура обработчика, фабрики, время жизни, ID эффектов фабрик.
- Не входят: DI для мидлварей сообщений, поведение фабрик в durable-режиме, atomic и query.

## Решение

- **Два непересекающихся набора зависимостей.** Зависимости эффектов — инфраструктура и ресурсы: подключение к БД, клиент внешнего сервиса. Зависимости сообщений — данные для обработчика: аутентификация, проверка прав. Они разные по природе: первые асинхронные и управляют ресурсами, вторые детерминированные и получают данные только через эффекты. Графы строятся раздельно: зависимость, которой нет в своём наборе, не найдена, даже если она есть в другом.
- **DI сообщений живёт в движке операций,** DI эффектов — в Environment. Так наборы разделены физически, а эффекты фабрик сообщений движок превращает в инструкции так же, как эффекты обработчика.
- **Общие принципы те же, что в DI эффектов:** сопоставление по типу и имени, всё проверяется и готовится заранее, зависимость может зависеть только от зависимостей с таким же или более долгим временем жизни. Сообщение и его контекст — встроенные зависимости. Тип сообщения у обработчика известен заранее, поэтому сообщение сопоставляется по общим правилам, в том числе по базовому классу.
- **Фабрика** — готовый объект или генераторная функция, которая yield-ит эффекты и возвращает зависимость. Кода закрытия нет.
- **Фабрике разрешены только чтение и внутренние эффекты.** Статически это задаёт аннотация, в рантайме проверяет движок.
- **Время жизни:** приложение и сообщение. Зависимости приложения создаются на старте Environment, после зависимостей эффектов. Зависимости сообщения — перед вызовом обработчика. И те и другие — последовательно, в заранее посчитанном порядке.
- **У каждой операции своё время жизни сообщения:** вложенная команда и каждый обработчик события не наследуют зависимости родительской операции.
- **У каждой фабрики сообщения свой детерминированный поток ID эффектов,** выведенный из ID сообщения и ключа зависимости. Поэтому добавление или изменение зависимости не сдвигает ID эффектов обработчика. У фабрик приложения ID сообщения нет, ID их эффектов случайные.

## Развилки

### Возврат зависимости: управляющий эффект с закрытием или `return`

- Выбрано: фабрика возвращает зависимость через `return`, кода закрытия нет.
- Почему: других применений, кроме аутентификации, проверки прав и подготовки данных, не видно. Ресурсы ушли в зависимости эффектов, сквозная логика — в мидлвари, закрывать нечего. А закрытие усложняет durable-режим, время жизни приложения и отмену: при закрытии генератора yield-ить эффекты нельзя. С `return` правило «ровно одна зависимость» гарантирует язык, а не проверка в рантайме.
- Отвергнуто: управляющий эффект «вернуть зависимость» и код закрытия после него, как было в концепте.

### Какие эффекты разрешены фабрике

- Выбрано: только чтение и внутренние эффекты, для всех видов обработчиков одинаково.
- Почему: чтение безопасно повторять, поэтому фабрики можно перезапускать при ретраях и не журналировать.
- Отвергнуто: разрешать фабрике то же, что обработчику, который её использует. Одна фабрика обслуживает обработчики разных видов, поэтому статически это не выразить.

### Один поток ID эффектов или свой у каждой фабрики

- Выбрано: свой поток у каждой фабрики.
- Почему: при общем потоке добавление или перестановка зависимости сдвигает ID эффектов обработчика. Это важно для durable-операций, которые не завершились в момент деплоя.

### Зависимости приложения

- Выбрано: создаются сразу на старте, могут yield-ить эффекты.
- Почему: как у зависимостей эффектов, ошибки видны сразу на старте. Эффекты нужны, чтобы, например, загрузить ключи проверки токенов из конфига.
- Отвергнуто: только готовые объекты или ленивые фабрики без эффектов.

### Недоступное время жизни сообщения у эффектов фабрик приложения

- Ситуация: фабрика приложения yield-ит эффект, а обработчику этого эффекта нужна зависимость эффектов со временем жизни сообщения. На старте сообщения нет, взять её неоткуда.
- Выбрано: ошибка в рантайме, Environment не стартует.
- Почему: заранее это можно проверить только по типам эффектов из аннотации фабрики, а их почти никогда не перечисляют точно.

## Нюансы

- В durable-режиме фабрики при восстановлении не перезапускаются: сохраняются аргументы, с которыми вызван обработчик. Значит, зависимости сообщений должны сериализоваться.
- Составной сид потока ID должен быть однозначным: иначе ID эффектов фабрики одного сообщения могут совпасть с ID эффектов обработчика другого сообщения, у которого ID подобран неудачно.
- Сид фабрики строится из имени и типа зависимости, без обязательного стабильного имени. Переименование типа зависимости меняет ID её эффектов — так же, как изменение кода обработчика.

## Сочетание с другими фичами

- Мидлвари сообщений: получают ли они параметры через этот DI и охватывает ли их время жизни сообщения — решить вместе с мидлварями.
- Durable: сериализация зависимостей сообщений.
- Запросы: когда появятся, фабрикам можно будет их вызывать — это тоже чтение.
