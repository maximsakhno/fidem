# 0010. Миграции системных таблиц

- Статус: реализовано
- Дата: 2026-11-25
- PR: #16
- Связано: 0008 (транзакции БД), 0009 (запросы и транзакции); README → «Миграции», «asyncpg», «События»

## Контекст

Фреймворку нужны свои системные таблицы в дополнение к таблицам приложения: outbox, а позже журнал durable-режима, расписание, хранилище идемпотентности. Одни нужны базовой функциональности, другие — опциональным расширениям, встроенным или пользовательским. Таблицы надо создавать и обновлять вместе с версиями fidem. Ближайший повод — outbox.

## Цель и границы

- Входит: механизм миграций для драйвера asyncpg — секции, учёт применённых версий, защита от параллельного запуска и от изменённых миграций.
- Не входят: применение миграций на старте Environment, CLI, проверка актуальности схемы, миграции данных, откат миграций, зависимости между секциями, миграции вне транзакции, настраиваемое имя схемы, публичный загрузчик миграций из файлов, ORM-драйверы.
- Механизм делается вместе с первой реальной таблицей — outbox.

## Решение

- **Миграции — забота драйвера, ядро о них не знает.** Таблицы нужны не ядру, а реализациям его интерфейсов в драйвере: ядро объявляет «записать события в текущую транзакцию», а таблица outbox появляется в `fidem.asyncpg`. У реализации БД в памяти миграций нет, у ORM свои инструменты.
- **Секция** — миграции таблиц одного компонента на одном драйвере: outbox на asyncpg, идемпотентность на asyncpg, расширение пользователя на asyncpg. Секции независимы, у каждой своя последовательность версий. Пользователь, который пишет расширение или свой драйвер, даёт свои секции.
- **Миграция — SQL-строка, только вперёд.** SQL можно хранить файлом и при желании применить чужим инструментом. Down-миграции в проде почти не используют, и их не тестируют.
- **Применение — явный вызов `migrate(pool, sections)`.** Список секций собирает приложение, вызов оно добавляет само, например шагом деплоя.
- **Учёт** — таблица применённых версий с хешем SQL. Изменённая применённая миграция — ошибка до применения чего-либо.
- **Таблицы fidem — в отдельной схеме `fidem`.**

## Развилки

### Свой механизм или чужой инструмент

- Выбрано: свой небольшой раннер в пакете драйвера. SQL миграций доступен как данные, поэтому вариант «только SQL» достаётся бесплатно.
- Почему: если только отдавать SQL, пользователь при каждом обновлении fidem переносит миграции в свой инструмент вручную, и это легко забыть.
- Отвергнуто:
  - только SQL-файлы, применяет пользователь своим инструментом — ручной перенос при обновлениях;
  - интеграция с Alembic — тянет SQLAlchemy, для голого asyncpg это лишнее. Подходит будущему ORM-драйверу.
- Таблицы приложения мигрирует его собственный инструмент, раннер с ним не конкурирует.

### Применять ли миграции на старте Environment

- Выбрано: нет, только явный вызов.
- Почему: реплики стартуют одновременно, у приложения в проде часто нет прав на DDL, деплой обычно мигрирует отдельным шагом. Кому нужно на старте — добавляет вызов сам.
- Отвергнуто: опция «применить на старте» — готовой функции достаточно.
- Отложено: проверка на старте, что схема актуальна, — нет реальной потребности, а повторный `migrate` и так ничего не делает.

### Кто собирает список секций

- Выбрано: приложение, явным списком.
- Почему: проще, миграции не связаны с DI, и для миграции не нужно собирать Environment.
- Отвергнуто: собирать секции из того, что подключено в Environment, — так секцию не забыть, но DI связывается с миграциями.

### Где лежат таблицы fidem

- Выбрано: отдельная схема с фиксированным именем `fidem`.
- Почему: таблицы фреймворка не смешиваются с бизнес-таблицами.
- Отвергнуто: префикс `fidem_` в схеме приложения — таблицы смешиваются.
- Отложено: настраиваемое имя схемы (например, несколько приложений в одной БД) — его пришлось бы подставлять в SQL миграций и в запросы драйвера.

### Версии в БД новее, чем в коде

- Выбрано: пропускать без ошибки.
- Почему: при rolling deploy старые реплики ещё работают с новой схемой, ошибка сломала бы их.

## Нюансы

- Каждая миграция — в своей транзакции вместе с записью о ней: DDL в PostgreSQL транзакционный, поэтому упавшая миграция откатывается целиком, а предыдущие остаются.
- Параллельные запуски сериализуются advisory lock: саму таблицу применённых версий заблокировать нельзя, её может ещё не быть. Lock берётся в транзакции каждой миграции, а не на весь прогон в сессии: через пулер в transaction mode сессионные lock и unlock могут уйти на разные соединения сервера, и lock останется взятым навсегда. Поэтому в транзакции миграция перепроверяет, не применил ли её параллельный запуск.
- Схема `fidem` создаётся, только если её нет: `CREATE SCHEMA IF NOT EXISTS` проверяет право создавать схемы в базе раньше, чем существование схемы, а у роли мигратора его может не быть.
- Миграции — список или кортеж, а не любая последовательность: строка — тоже последовательность строк, и каждый её символ стал бы миграцией.
- Имена секций уникальны, у секций fidem — префикс `fidem.`, чтобы не пересечься с секциями пользователя. Расширению пользователя рекомендуется своя схема, а не `fidem`.
- Логи применённых миграций подставляют значения в сообщение, а не в `extra`: при обычной настройке логирования `extra` не выводится.

## Сочетание с другими фичами

- Outbox: первая секция `fidem.outbox` с таблицей outbox.
- Расширения вроде идемпотентности дают свою секцию на каждый драйвер, где они реализованы.
- Будущий ORM-драйвер может положить секции на свой инструмент, например ветки Alembic.

## Открытое

- Проверка актуальности схемы на старте — когда понадобится fail fast при забытой миграции.
- CLI — когда вызов функции станет неудобен.
- Миграции данных функциями и миграции вне транзакции (`CREATE INDEX CONCURRENTLY`) — с первой такой миграцией.
- Зависимости между секциями — с первым примером.
- Публичный загрузчик миграций из файлов — когда понадобится пользователю.
