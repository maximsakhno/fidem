# 0009. Запросы и транзакции как эффекты

- Статус: реализовано
- Дата: 2026-11-25
- PR: #14
- Пересмотрено: 0013 (события staged копятся в памяти и пишутся после возврата обработчика, а не сразу с пометкой «операция не завершилась»); 0014 (неявная транзакция — обычная транзакция из одного эффекта, её создаёт движок; одиночное чтение идёт без транзакции БД благодаря настройкам драйвера для неявной читающей транзакции)
- Связано: 0005 (гарды), 0007 (мидлвари сообщений), 0008 (транзакции БД и atomic-команды); README → «Query», «Staged», «Atomic», «Транзакции БД», «asyncpg», «Гарды»

## Контекст

Запросов не было, и чтение приходилось оформлять staged-командой. Кроме того, читать можно было только отдельными эффектами, каждый в своей неявной транзакции. Согласованно прочитать несколько запросов в одной транзакции БД было нельзя, а явная транзакция существовала только как результат atomic-команды.

## Цель и границы

- Входит: запросы, читающие и пишущие транзакции, которые обработчик yield-ит как эффекты, настройки транзакций в asyncpg.
- Не входят: вложенные запросы и команды из обработчиков, события и обработчики событий, savepoint-ы, ретрай транзакции, durable-режим.

## Решение

- **Запрос** обрабатывается как команда, которая только читает и в конце возвращает результат. У Environment и движка для него отдельный метод `query`. Гарды и мидлвари работают как у команды. Режим всегда ephemeral, поэтому `execution_mode` есть только в объявлениях команд.
- **Один набор эффектов «только чтение»** (`QueryEffect`) для обработчика запроса, гардов и первой фазы atomic: по сути это одно и то же.
- **Мидлварь запроса может писать**, например кеш сохраняет результат: запрет записи касается обработчика, а не всей цепочки.
- **Транзакция — объект, который объявляется на уровне модуля** декоратором над функцией с любыми параметрами. Вызов объекта с аргументами — эффект, поэтому транзакцию yield-ят, как любой эффект. Аргументы заменяют замыкание.
- **Два вида транзакций:**
  - читающая содержит только чтения БД, чтобы прочитать данные из одного снимка;
  - пишущая содержит любые эффекты БД.

  Запрос, гард и первая фаза atomic yield-ят читающие транзакции. Staged-обработчик и мидлварь сообщения yield-ят оба вида в любом количестве. Atomic в конце возвращает одну пишущую транзакцию — то, что раньше было функцией транзакции.
- **Транзакции исполняет движок**, и эффектами БД они не являются. Поэтому вложенную транзакцию запрещают типы.
- **Эффекты транзакции продолжают последовательность ID** того, кто её yield-ит, как запись в atomic.
- **Ядро ничего не знает о настройках транзакций.** В контекст транзакции оно передаёт сам объект транзакции, и драйвер по нему находит свои настройки.
- **В asyncpg:**
  - читающая транзакция открывается как `READ ONLY` и по умолчанию работает в repeatable read;
  - неявное чтение транзакцию не открывает;
  - настройки задаются раздельно для читающих и пишущих транзакций и переопределяются для отдельной транзакции.
- **Staged-обработчик получил свой тип генератора**, как atomic и query, и общий тип обработчика сообщения стал не нужен.

## Развилки

### Имя метода запроса

- Выбрано: `query`. Получается тройка «глагол + сообщение»: `execute(command)`, `publish(event)`, `query(query)`.
- Отвергнуто:
  - `ask` — смысл не очевиден без знания Akka;
  - `fetch` — ассоциируется с HTTP;
  - `send` для команд — не говорит, что вернётся результат;
  - один `send` для команд и запросов, как в MediatR, — методы не различают смысл, а тип возврата и режимы у них разные;
  - `dispatch` и `handle` — ничего не говорят о роли сообщения.

### Как обработчик получает транзакцию

- Выбрано: транзакция — эффект. Atomic возвращает его так же, как внешнюю запись: один эффект записи.
- Почему: функцию нельзя yield-ить, а staged-обработчику, первой фазе atomic и запросу нужно yield-ить транзакции.
- Цена: просто функцию из atomic вернуть уже нельзя, транзакцию надо объявить декоратором.

### Где объявлять транзакцию

- Выбрано: на уровне модуля, данные — аргументами вызова.
- Почему: на объект транзакции можно сослаться в настройках драйвера.
- Цена: данные, которые раньше приходили из замыкания, передаются аргументами.
- Транзакцию по-прежнему можно объявить внутри обработчика, но тогда она всегда получает настройки по умолчанию: объект создаётся заново при каждом вызове, и сослаться на него нельзя.

### Кто исполняет транзакцию

- Выбрано: движок, как управляющие эффекты.
- Почему: вложенная транзакция исключена типами — внутри транзакции разрешены только эффекты БД.
- Цена: в типах эффектов запроса, гарда и первой фазы atomic читающую транзакцию приходится перечислять явно.
- Отвергнуто: транзакция как наследник эффектов БД — тогда типы разрешали бы её внутри другой транзакции.

### Где задавать настройки транзакции

- Выбрано: в объявлении драйвера, по объекту транзакции.
- Почему: настройки ближе к месту, где они нужны, и различают несколько транзакций одной команды.
- Отвергнуто:
  - по типу сообщения, как в 0008, — не различает транзакции одной команды; настройки были нужны, пока у транзакции не было своего объекта;
  - уровень изоляции в ядре, полем транзакции, — ядро не должно знать деталей транзакции: может быть БД без уровней изоляции, а у разных БД разные уровни.

### Уровни настроек в asyncpg

- Выбрано: настройки читающих транзакций, настройки пишущих транзакций и переопределение для отдельной транзакции. Значения по умолчанию — repeatable read для чтения и read committed для записи.
- Почему: параметров столько же, сколько видов транзакций, нет цепочки поиска «вид → общие → встроенные», а значение по умолчанию видно сразу.
- Цена: чтобы задать один уровень и чтению, и записи, его передают дважды.
- Отвергнуто:
  - ещё и общие настройки для обоих видов — их было в реализации, убрали после ревью: не нашлось примера из приложения, где они нужны;
  - только общие настройки и переопределение по транзакции — отдельно настроить все читающие или все пишущие транзакции было бы нельзя.

### Неявное чтение

- Выбрано: никогда не открывает транзакцию. Это пересмотр 0008: там неявное чтение открывало транзакцию, если уровень изоляции выше read committed.
- Почему: одно чтение и так видит один снимок, а несколько согласованных чтений теперь делаются через читающую транзакцию. Настройки описывают только явные транзакции, и их проще объяснить.
- Отвергнуто:
  - брать настройки читающих транзакций — по умолчанию там repeatable read, и на каждое одиночное чтение придутся лишние `BEGIN` и `COMMIT`;
  - отдельные настройки для неявного чтения — избыточно.
- Обработчик, которому внутри одного эффекта нужно несколько запросов из одного снимка, открывает транзакцию сам.

### Что транзакция сообщает фабрике

- Выбрано: признак «только чтение» и сам объект транзакции, у неявной транзакции объекта нет.
- Почему: фабрике надо отличить одиночное чтение от явной читающей транзакции, иначе одиночное чтение получило бы repeatable read, а явная транзакция — read committed. Объект нужен, чтобы найти настройки, поэтому отдельный флаг «неявная» не понадобился.

### Явная читающая транзакция при read committed

- Выбрано: транзакция не открывается, без ошибки и без скрытого повышения уровня: это выбор пользователя.
- Почему: при read committed каждый запрос и так видит свой снимок, и транзакция ничего не даёт.
- Цена: запись в такой транзакции БД не запрещает.

## Нюансы

- В PostgreSQL транзакция на уровне read committed не даёт согласованного чтения: каждый запрос в ней видит свой снимок. Поэтому по умолчанию читающая транзакция работает в repeatable read. Тест проверяет оба случая: коммит из другого соединения между двумя чтениями транзакции.
- Ошибка вызова функции транзакции, например неподходящие аргументы, должна попадать в обработчик так же, как другие ошибки транзакции. Поэтому функция вызывается при выполнении транзакции, а не когда движок готовит инструкцию.
- Pyright считает параметры типов frozen-датаклассов инвариантными. Из-за этого транзакция без событий не подходила туда, где ждут транзакцию с событиями, и atomic-обработчики без событий не проходили проверку типов. Параметры типов транзакций объявлены ковариантными явно.
- Конкурентные serializable-транзакции падают с ошибками сериализации, и без ретрая их не выполнить параллельно. Поэтому в примере переводы идут друг за другом.

## Сочетание с другими фичами

- Мидлвари сообщений: общий список действует и на запросы. Мидлварь может yield-ить транзакции обоих видов.
- Гарды: могут читать через читающие транзакции, вложенные запросы — позже.
- Outbox: пишущая транзакция atomic будет yield-ить события и писать их в outbox той же транзакцией. Для staged пока только идея: события его транзакций сразу пишутся в outbox с пометкой, что операция ещё не завершилась и обрабатывать их рано, а после успешного завершения операции все её события помечаются готовыми к обработке.
- Durable: решить, как журналировать транзакции и их ID и как сериализовать аргументы транзакций.

## Открытое

- Вложенные запросы и команды из обработчиков — вместе с семантикой вложенных сообщений.
- Транзакции в обработчиках событий — вместе с событиями.
- Отдельные типы настроек для читающих и пишущих транзакций — когда появится настройка только одного вида, например `DEFERRABLE` для чтения.
- Ретрай транзакции, в том числе при ошибках сериализации, и savepoint-ы.
