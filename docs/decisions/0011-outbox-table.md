# 0011. Таблица outbox

- Статус: реализовано
- Дата: 2026-11-25
- PR: #16
- Пересмотрено: 0013 (строки по обработчикам разворачивает драйвер из записи события, а не движок)
- Связано: 0008 (транзакции БД), 0010 (миграции системных таблиц); README → «События», «Миграции»

## Контекст

Outbox — этап 2 плана atomic-команд с событиями (0008): события пишутся в outbox той же транзакцией, что и данные, а диспетчер доставляет их обработчикам. Задача большая, поэтому начата с таблицы: на её устройство опираются и запись событий, и диспетчер.

## Цель и границы

- Входит: таблица outbox в PostgreSQL как секция миграций `fidem.outbox`.
- Не входят: сериализация событий, их объявления и объявления обработчиков, запись в outbox из движка, диспетчер, очистка обработанных строк, сохранение породивших операций, `correlation_id` и заголовки.

## Решение

- **Payload события — jsonb.** Всё в fidem будет сериализоваться в JSON: это стандарт, он читаем, по jsonb можно искать по полям. Вокруг JSON есть экосистема, на которой строятся будущие фичи: по JSON Schema команды — форма отправки в дашборде, по JSON-RPC — API приложения без ручного кода.
- **Строка — доставка события одному обработчику.** Обработчиков у события 0..N, каждый выполняется отдельной операцией, поэтому статус, попытки и время следующей попытки у каждого свои.
- **`id` строки — `message_id` операции обработчика**, выведенный из ID события и имени обработчика. Строку и операцию можно связать без отдельной колонки, а повторная запись той же доставки упирается в первичный ключ.
- **Ссылки:** ID события, общий для всех его строк, и `message_id` операции, которая опубликовала событие.
- **`available_at`** — когда строку можно взять. Это и время следующей попытки, и конец аренды: диспетчер берёт строку, сдвигая `available_at`, и если он упал, строку после этого времени возьмёт другой. Отдельная колонка блокировки не нужна.
- **Обработанные строки остаются** со статусом `done` для истории в дашборде и отладке. Выборку необработанных держит быстрой частичный индекс по `pending`.

## Развилки

### Одна таблица или события отдельно от доставок

- Выбрано: одна таблица, строка на пару «событие × обработчик».
- Почему: проще — одна вставка, без join.
- Цена: payload дублируется по обработчикам, а событие без обработчиков не пишется вовсе.
- Отвергнуто: таблица событий плюс таблица доставок.

### Сохранять ли породившие операции

- Выбрано: пока только ссылка `source_message_id`.
- Почему: обработчику события содержимое команды не нужно, а сохранённые операции нужны другим фичам — журналу durable-режима и идемпотентности на входе. Таблица операций появится с ними.
- Отложено: сохранение операций и ссылка на их таблицу.

### Тип статуса

- Выбрано: enum PostgreSQL.
- Почему: тип самодокументируется.
- Цена: значение enum нельзя удалить без пересоздания типа, а новое значение нельзя использовать в той же транзакции, где его добавили, — такую миграцию придётся разбить на две.
- Отвергнуто: `text` с `CHECK`.

### Удалять ли обработанные строки

- Выбрано: оставлять.
- Почему: история доставок нужна дашборду и для отладки.
- Цена: таблица растёт, нужна очистка.

## Нюансы

- `last_error` — пока текст: формат ошибки решится вместе с диспетчером, в jsonb его можно перевести миграцией.

## Сочетание с другими фичами

- Сериализация: payload и версия события пишутся ею. Без неё запись в outbox не сделать.
- Запись событий: движок знает обработчиков события при записи и пишет строку на каждого. Повтор транзакции, например ретрай-мидлварью, пишет те же `id`, и вставка должна их пропускать.
- Диспетчер: берёт `pending`-строки с прошедшим `available_at`, увеличивает `attempts`, сдвигает `available_at` на время аренды, после успеха ставит `done` и `processed_at`, после ошибки — `last_error` и новое `available_at`, после последней попытки — `failed`.
