# 0012. Сериализация

- Статус: реализовано
- Дата: 2026-11-25
- PR: #18
- Связано: 0011 (таблица outbox); README → «Сериализация»

## Контекст

Чтобы писать события в outbox, их надо переводить в JSON и обратно: payload — jsonb (0011). Журналу durable-режима понадобится то же для эффектов, их параметров и результатов. Кроме того, по типу нужна JSON Schema: на ней строятся форма отправки события в дашборде и документация API.

## Цель и границы

- Входит: интерфейс сериализации в ядре и реализации на pydantic и msgspec.
- Не входят: подключение сериализатора к движку и Environment, запись в outbox, реестр имён и версий сообщений, апкаст старых версий, общие компоненты схем для нескольких типов, кеш кодеков в интерфейсе.

## Решение

- **Интерфейс — в ядре, реализации — вне его.** Библиотеку выбирает пользователь: pydantic или msgspec, обе — опциональные зависимости. Можно подключить свою реализацию. Реализации по умолчанию нет, поэтому ядро остаётся без зависимостей.
- **Тип — любой, а не только класс сообщения или эффекта.** Результаты эффектов бывают какими угодно: `list[User]`, `User | None`.
- **Сериализатор по типу готовит кодек.** Кодек переводит значения одного типа в JSON и обратно и строит JSON Schema входа.
- **Свои ошибки:** неподдерживаемый тип, несериализуемое значение, данные не того вида. По ним потребитель, например диспетчер outbox, отличает битые данные от прочих ошибок, не импортируя библиотеку.
- **Сериализатор знает только соответствие типа и JSON.** Тип по имени и версии сообщения находит реестр объявлений, а не сериализатор.

## Развилки

### Три метода с типом или фабрика кодеков

- Выбрано: сериализатор по типу отдаёт типизированный кодек.
- Почему: неподдерживаемый тип ловится при подготовке, а не при первой записи, как в DI. Дорогая подготовка кешируется в кодеке. Десериализация статически возвращает нужный тип.
- Отвергнуто: три метода сериализатора, каждый принимает тип, — ошибки типа видны только при использовании, подготовку пришлось бы кешировать отдельно.

### Python-значения или готовый JSON

- Выбрано: обе формы.
- Почему: Python-значения легко вложить в общую структуру — запись журнала, конверт JSON-RPC. Готовый JSON быстрее: библиотеки пишут его сразу в байты.
- Отложено: убрать форму, которая окажется не нужна.

### Нужен ли тип при сериализации

- Выбрано: да, кодек привязан к типу и в обе стороны.
- Почему: по одному значению не сериализовать объединения и обобщённые коллекции.

### Как типизировать параметр типа

- Выбрано: перегрузки: класс даёт кодек этого типа, всё остальное — кодек `Any`.
- Цена: тип кодека для объединения приходится писать явно.
- Отвергнуто: `TypeForm` из `typing_extensions` — зависимость ядра и экспериментальный режим basedpyright.
- Отложено: переход на `TypeForm`, когда он появится в стандартной библиотеке.

### Строгость декодирования

- Выбрано: по умолчанию — поведение библиотеки, настройка `strict` в конструкторе. Единую семантику интерфейс не обещает.
- Почему: библиотеки ведут себя по-разному: pydantic приводит `"1"` к `1`, msgspec нет. Подгонять одну под другую — значит воевать с библиотекой.

### Проверка, что значение соответствует типу

- Выбрано: при сериализации не обещается.
- Почему: msgspec пишет значение по его фактическому типу. Pydantic по умолчанию лишь предупреждает о несоответствии; его предупреждение превращено в ошибку, но и он пропускает, например, dataclass другого типа с теми же полями.

### Совместимость форматов между библиотеками

- Выбрано: не гарантируется.
- Почему: одни и те же типы, например `datetime`, библиотеки могут писать по-разному. Смена сериализатора на сохранённых данных — забота приложения.

### Настройки реализаций

- Выбрано: только `strict`.
- Почему: фича делается только при реальном примере, а другим настройкам его пока нет.
- Отложено: хуки msgspec для своих типов и прочие настройки — до реальной потребности.

## Нюансы

- Pydantic в строгом режиме из Python-значений принимает только Python-объекты: dataclass, а не словарь. Поэтому Python-значения он декодирует через JSON, это лишний проход.
- Pydantic по умолчанию читает поля по алиасам, а пишет по именам. Чтобы записанное читалось, он пишет по алиасам.
- Декодер msgspec принимает любой тип, потому что рассчитан на хуки. Неподдерживаемый тип ловит построение схемы, поэтому схема строится при подготовке кодека.
- В Python-значениях msgspec могут оставаться кортежи там, где в JSON списки. Поэтому формы согласованы по JSON, а не по равенству Python-объектов.

## Сочетание с другими фичами

- Outbox: payload события — его кодек, тип находится по имени и версии события. Где хранится сериализатор и кто готовит кодеки, решится вместе с записью в outbox. Удобно готовить кодеки объявленных сообщений при создании движка, тогда неподдерживаемый тип всплывёт на старте.
- Драйвер asyncpg: для jsonb он по умолчанию ждёт строку, поэтому драйвер декодирует байты.
- Журнал durable-режима: параметры и результаты эффектов — произвольные типы, поэтому интерфейс сразу на них рассчитан.
- Дашборд и документация API строятся по JSON Schema. Для OpenAPI понадобятся общие компоненты схем для нескольких типов.
