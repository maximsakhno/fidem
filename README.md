fidem — Python-фреймворк для бизнес-логики. Его цель — дать из коробки то, что обычно пишут вручную в каждом обработчике: outbox, ретраи, идемпотентность, восстановление после падения процесса, логи, метрики и трассировку.

Фреймворк может это дать, потому что бизнес-логика не выполняет побочные эффекты сама, а описывает их. Обработчик сообщения — генератор: он yield-ит описание действия, эффект, и получает обратно результат. Выполняет действие фреймворк. Такой подход называют системой эффектов.

Поэтому фреймворк знает о приложении почти всё. Из кода — какие есть сообщения и обработчики, кто кого вызывает и что каждому обработчику разрешено делать. Во время работы — каждое выполненное действие, его результат и длительность. На этом знании строятся все возможности фреймворка, в том числе [будущие](#что-ещё-можно-построить-на-знании-о-приложении).

Этот документ — единый источник истины об устройстве фреймворка. Почему решения приняты именно так, объясняют [записи о решениях](docs/decisions/README.md). Фреймворк в разработке, поэтому у каждой возможности есть статус:

- ✅ реализовано;
- 📋 запланировано;
- ❓ надо продумать.

## Установка

Нужен Python 3.13 или новее. Драйвер PostgreSQL и сериализатор ставятся как extras:

```shell
uv add "fidem[asyncpg,pydantic] @ git+https://github.com/maximsakhno/fidem"
```

## Пример

Команда переименовывает пользователя, запрос возвращает его. Обработчики сообщений только описывают действия: читают пользователя эффектом `GetUserEffect` и сохраняют его в пишущей транзакции. С БД работают обработчики эффектов, соединение им подставляет [DI](#di). `Fidem` собирает объявления вместе и выполняет сообщения.

```python
@dependency
async def pool() -> AsyncGenerator[Pool]:
    async with create_pool(DATABASE_URL) as pool:
        yield pool


@effect("get_user")
@dataclass(frozen=True, slots=True)
class GetUserEffect(DatabaseReadEffect[User]):
    user_id: str


@effect_handler
async def handle_get_user(connection: Connection, effect: GetUserEffect) -> User: ...


@effect("save_user")
@dataclass(frozen=True, slots=True)
class SaveUserEffect(DatabaseWriteEffect[User]):
    user: User


@effect_handler
async def handle_save_user(connection: Connection, effect: SaveUserEffect) -> User: ...


@command("rename_user")
@dataclass(frozen=True, slots=True)
class RenameUserCommand(Command[User]):
    user_id: str
    name: str


@dataclass(frozen=True, slots=True)
class GetUserQuery(Query[User]):
    user_id: str


@WriteTransaction
def save_user(user: User) -> WriteTransactionEffectful[User]:
    return (yield from SaveUserEffect(user))


@command_handler
def rename_user(command: RenameUserCommand) -> AtomicEffectful[User]:
    user = yield from GetUserEffect(command.user_id)
    return save_user(replace(user, name=command.name))


@query_handler
def get_user(query: GetUserQuery) -> QueryEffectful[User]:
    return (yield from GetUserEffect(query.user_id))


fidem = Fidem(modules=[myapp], definitions=[AsyncpgDatabase(pool)])
async with fidem:
    user = await fidem.handle(RenameUserCommand("u1", "Alice"), message_id="request-42")
    user = await fidem.handle(GetUserQuery("u1"))
```

- [зависимости](examples/02_dependencies.py);
- [гарды](examples/03_guards.py);
- [мидлвари эффектов](examples/04_effect_middlewares.py);
- [мидлвари сообщений](examples/05_message_middlewares.py);

Запуск — `uv run python -m examples.events.in_memory`.

## Пользовательский API

✅ Приложение объявляется декораторами и собирается классом `Fidem`. Каждое объявление сводится к объявлению [ядра](#архитектура), поэтому разделы ниже описывают оба: сначала декоратор, затем объект ядра.

| Декоратор | На что | Параметры | Объявление ядра |
| --- | --- | --- | --- |
| `@command(name, version=1)` | класс команды | — | имя и версия `StagedCommandDef` / `AtomicCommandDef` |
| `@event(name, version=1)` | класс события | — | `EventDef` |
| `@effect(name, version=1)` | класс эффекта | — | имя и версия `EffectDef` |
| `@guard_input` | класс входа гардов | — | `GuardInputDef` |
| `@command_handler` | обработчик команды | `middlewares`, `mode` | `StagedCommandDef` / `AtomicCommandDef` |
| `@query_handler` | обработчик запроса | `middlewares` | `QueryDef` |
| `@event_handler` | обработчик события | `name`, `middlewares`, `mode` | обработчик в `EventDef` |
| `@guard` | гард | `name`, `type` | `GuardDef` |
| `@effect_handler` | обработчик эффекта | `middlewares` | `EffectDef` |
| `@dependency` | фабрика зависимости | `lifetime`, `name`, `type` | `EffectDependencyDef` |
| `@middleware` | мидлварь сообщения | `name` | `MessageMiddlewareDef` |
| `@effect_middleware` | мидлварь эффекта | — | `EffectMiddlewareDef` |

- **Декоратор возвращает саму функцию или класс** и помечает их, поэтому обработчик вызывается в тесте как обычная функция. Пометка — только одна: функция с двумя декораторами fidem — `AlreadyDeclaredError`. Bound-метод пометить нельзя (`UnsupportedFunctionError`), его оборачивают функцией. Глобального реестра нет: помеченное попадает в приложение, только если его передали или нашли в модулях.
- **Вывод из аннотаций.** Тип сообщения — из параметра, аннотированного подклассом `Command`, `Query` или `Event`, тип эффекта — из параметра-подкласса `Effect`, кроме сообщений. Такой параметр ровно один, иначе `HandledTypeError`. Ошибки объявлений пользовательского API — в модуле `fidem.errors`. Вид обработчика команды и события — из типа результата: `AtomicEffectful` — atomic, `StagedEffectful` — staged, их псевдонимы тоже подходят, другой тип — `UnsupportedReturnTypeError`. У обычной функции результат `WriteTransactionEffect` или подкласс `ExternalWriteEffect` — atomic, остальное — staged. Аннотации читаются при создании `Fidem`, а не в декораторе, поэтому обработчик может ссылаться на класс, объявленный ниже.
- **Имена.** Команды, события и эффекты хранятся по имени и версии, поэтому их задают явно декоратором класса, а не выводят из имени класса. Класс без декоратора у обработчика команды, события или эффекта — `UndeclaredClassError`, подкласс объявленного класса объявляется сам. У запроса имени нет. Имя обработчика события и мидлвари сообщения по умолчанию — имя функции.
- **Мидлвари** передаются в `Fidem` явными списками, потому что важен порядок: первая — внешняя. Мидлварь — функция или объявление: `@middleware(name=...)` задаёт мидлвари сообщения другое имя, `@effect_middleware` пока без настроек. Мидлварь не ищется автодискавери и не передаётся в `definitions`. `middlewares` в декораторе обработчика заменяют общий список, `()` отключает мидлвари.
- **Настройки** гарды и мидлвари получают эффектом, обработчик которого берёт объект из DI, например `yield from VerifyTokenEffect(token)` с `TokenVerifier` в зависимостях. Замыкание тоже работает.

✅ `Fidem(*, modules=(), definitions=(), middlewares=(), effect_middlewares=(), stdlib=True)` собирает движок и Environment и даёт только `handle(message, *inputs, message_id=None)` и `async with`.

- **`definitions`** — объявления пользовательского API, классы с `@event` или `@guard_input` и объявления ядра, например `AsyncpgConnectionDef()` или `outbox.effect_defs`. Другой объект — `UnsupportedDefinitionError`. Объект, переданный дважды или найденный ещё и в модулях, считается одним.
- **Обычная функция** вместо генераторной — у обработчиков команд, событий и запросов и у гардов, которым не нужны эффекты. `Fidem` оборачивает её в генераторную функцию с той же сигнатурой: atomic-обработчик возвращает запись, staged — результат, гард — значение. Тайпчекер не проверяет, что atomic-обработчик вернул запись, это проверяет движок (`UnsupportedAtomicResultError`). Мидлварь — только генераторная функция, иначе она не вызовет `Proceed`. Async-функцию и класс `Fidem` не оборачивает, их отвергает ядро.
- **Зависимости короче фабрики.** `@dependency` на async-функции объявляет зависимость, которую не нужно закрывать: функция возвращает её. `instance(obj, name=, type=)` объявляет готовый объект, его тип по умолчанию — класс объекта.
- **`Bundle(*definitions)`** — пачка связанных объявлений, например частей драйвера, которые подключаются вместе. `Fidem` ставит на место набора его содержимое в том же порядке, наборы вкладываются друг в друга. Автодискавери наборы не ищет, их передают явно. Outbox и драйвер БД — наборы.
- **Событие** объявляет каждый его обработчик, поэтому `Fidem` сливает объявления одного события, а разные имя или версия — `DuplicateEventDefError`. Событие без обработчиков объявляет его класс.
- **`stdlib`** подключает обработчики [эффектов стандартной библиотеки](#эффекты-стандартной-библиотеки).

✅ **Автодискавери.** `modules` — объекты модулей. Модуль пакета сканируется вместе со всеми подмодулями. Из модуля берутся объявления, которые в нём определены, а импортированное из модуля вне сканирования пропускается: импорт не подключает чужой обработчик. Ошибка импорта подмодуля пробрасывается. Порядок объявлений — порядок списков и обхода модулей, он важен только сервисам.

## Модель

**Effectful-функция** — синхронная генераторная функция с типом `Effectful[R, E]`. Она yield-ит эффекты типа `E`, на каждый получает результат в той же точке кода и возвращает `R`. Тип эффектов входит в сигнатуру, поэтому то, что функции разрешено делать, видно и проверяется статически. ✅ В этой форме пишутся обработчики сообщений, [гарды](#гарды), [мидлвари сообщений](#мидлвари-сообщений) и [транзакции](#транзакции).

**Контракт детерминизма.** Effectful-функция при тех же входных данных и результатах эффектов yield-ит ту же последовательность эффектов. Поэтому она не делает ввода-вывода, а время, случайные числа и глобальное состояние получает только через эффекты. На этом контракте держатся ретраи, восстановление после падения и воспроизводимость. Сейчас фреймворк контракт не проверяет. 📋 Ловить попытки нарушить контракт, где это возможно.

**Типы.** Тип effectful-функции по возможности запрещает некорректные сочетания эффектов. ✅ В рантайме недопустимый эффект вызывает ошибку `UnsupportedEffectError`.

**Ошибки.** ✅

- **Ошибка эффекта** приходит в effectful-функцию через `generator.throw` в точке `yield from`, функция может поймать её и продолжить работу. Для составного эффекта — транзакции или `Proceed` — ошибкой считается непойманная ошибка его внутренней части.
- **Непойманная ошибка обработчика** завершает операцию и выходит из `handle`.
- **Ошибки самого фреймворка**, например недопустимый эффект, в effectful-функцию не приходят.
- **Прерванное выполнение** — отмена или закрытие плана — сразу закрывает генераторы, поэтому их `finally` и `with` отрабатывают.

### Масштабы выполнения

✅ Работа приложения делится на вложенные масштабы: операция порождает одну или несколько транзакций, транзакция — один или несколько эффектов. Эффекты БД всегда выполняются в [транзакции](#транзакции), остальные — прямо в операции.

| Масштаб    | Что это                                                  | Что даёт                                                                  | Скоуп [DI](#di) |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------------------------- | --------------- |
| Приложение | работа Environment                                       | общие ресурсы: пул соединений, клиенты                                    | `APPLICATION`   |
| Операция   | обработка одного сообщения: гарды, мидлвари и обработчик | ✅ ретраи, 📋 восстановление после падения, 📋 идемпотентность на входе     | `MESSAGE`       |
| Транзакция | эффекты БД в одной транзакции                            | ✅ согласованность, ✅ события в outbox той же транзакцией                 | `TRANSACTION`   |
| Эффект     | одно действие                                            | ✅ идемпотентность записи по `effect_id`                                   | `EFFECT`        |

## Эффекты

✅ Эффект — неизменяемое описание действия. Параметр типа задаёт тип результата: `GetUserEffect(DatabaseReadEffect[User])` возвращает `User`.

Категория эффекта определяет, кто его исполняет: [Environment или движок](#архитектура).

| Категория        | Что это                                                                                                       | Исполняет   |
| ---------------- | ------------------------------------------------------------------------------------------------------------- | ----------- |
| `InternalEffect` | Действие внутри процесса без внешних побочных эффектов: кеш, конфиг, случайные числа, обычный `asyncio.sleep` | Environment |
| `ExternalEffect` | Обращение к внешней системе: HTTP, брокер                                                                     | Environment |
| `DatabaseEffect` | Работа с собственной БД сервиса                                                                               | Environment |
| `ControlEffect`  | Управление выполнением: `Proceed`, [транзакции](#транзакции), 📋 параллельный запуск эффектов                  | Движок      |

Внешние эффекты и эффекты БД делятся на чтение и запись: `ExternalReadEffect`, `ExternalWriteEffect`, `DatabaseReadEffect`, `DatabaseWriteEffect`. Запись меняет состояние, поэтому её обработчик должен быть идемпотентным по `effect_id`: при ретрае и восстановлении операции запись повторяется с тем же ID.

`QueryEffect` объединяет эффекты, которые только читают: `InternalEffect`, `ExternalReadEffect`, `DatabaseReadEffect` и читающие транзакции. Чтение можно безопасно повторять.

✅ **Обработчик эффекта** — асинхронная функция, объявляется `@effect_handler`, в ядре — `EffectDef(name, effect_type, handler, version=1)`. У типа эффекта ровно один обработчик. Обработчик ищется по точному типу эффекта, наследование не учитывается. Сигнатура свободная: все параметры, включая сам эффект и `EffectContext`, подставляет [DI](#di).

✅ **Имя и версия эффекта** — стабильные, их задаёт `@effect` на классе. 📋 По ним журнал [durable-режима](#режимы-выполнения) хранит эффекты с параметрами и результатами. Имя уникально среди эффектов Environment, повтор — `DuplicateEffectDefError`. Имена встроенных эффектов — с префиксом `fidem.`: `fidem.now`, `fidem.write_outbox`. У control-эффектов объявления нет, как журналировать их — открытый вопрос durable-режима.

### Мидлвари эффектов

✅ Мидлвари эффектов оборачивают эффекты, которые исполняет Environment: эффект проходит мидлвари, затем DI и обработчик. Control-эффекты исполняет движок, поэтому мидлвари действуют не на них, а на эффекты внутри них.

Мидлварь эффекта (`EffectMiddleware`) — асинхронная функция `middleware(effect_call, call_next)`. `EffectCall` содержит сообщение, эффект и их контексты, мидлварь их только читает. `call_next()` вызывает следующую мидлварь, а после последней — обработчик эффекта.

- **Мидлвари работают до DI.** Поэтому каждый вызов `call_next` получает новые зависимости скоупа `EFFECT`, а ошибки создания и закрытия зависимостей видит как свои. Мидлвари эффекта БД работают внутри его [транзакции](#транзакции), явной или неявной.
- **`call_next` можно не вызывать или вызывать несколько раз.** Не вызывать — для кеша или заглушки, несколько раз — для ретрая, в том числе одновременно.
- **`call_next` после конца сообщения или транзакции** падает с `ScopeClosedError`, если обработчику нужна зависимость скоупа `MESSAGE` или `TRANSACTION`: её скоуп уже закрыт.
- **Ошибка мидлвари** — ошибка эффекта.
- **Регистрация** — `@effect_middleware`, `Fidem(effect_middlewares=...)` и `@effect_handler(middlewares=...)` для одного эффекта, в ядре — `EffectMiddlewareDef(middleware)`, `EnvironmentImpl(effect_middleware_defs=...)` и `EffectDef(..., middleware_defs=...)`. Список эффекта заменяет общий, `()` отключает мидлвари. Первая в списке — внешняя.
- **Зависимости** мидлварь получает через замыкание. ❓ Доступ к зависимостям скоупа `APPLICATION`.

### Эффекты стандартной библиотеки

✅ `fidem.core.stdlib` даёт эффекты для того, что [контракт детерминизма](#модель) запрещает вызывать напрямую:

- `NowEffect()` — текущее время в UTC с часовым поясом;
- `NewUuidEffect()` — случайный UUID версии 4;
- `RandomIntEffect(below)` — случайное целое от 0 до `below`, не включая `below`;
- `RandomBytesEffect(size)` — `size` случайных байт.

Случайные значения берутся из `secrets`, поэтому годятся для кодов подтверждения и токенов. Все эффекты — `InternalEffect`, поэтому их yield-ят и гарды, и запросы. `Fidem` подключает их обработчики сам, `stdlib=False` отключает. В ядре обработчики подключаются явно: `EnvironmentImpl(effect_defs=[*STDLIB_EFFECT_DEFS, ...])`.

Ретрай операции повторяет эти эффекты с теми же ID, но получает новые значения. Если запись прошла в первой попытке, во второй её пропустит идемпотентный по `effect_id` обработчик, и в БД останется UUID первой попытки, а обработчик сообщения продолжит работу с UUID второй. ❓ Возвращать при ретрае прежние значения по ID эффектов.

## Сообщения

✅ Сообщение — вход в бизнес-логику. Сообщение тоже эффект, поэтому обработчик ✅ публикует [события](#события) и 📋 сможет вызывать команды и запросы так же, как выполняет любой эффект. ❓ Семантика вложенных команд, особенно в staged-обработчиках.

| Тип          | Назначение         | Обработчиков на тип                             | Режим                 |
| ------------ | ------------------ | ----------------------------------------------- | --------------------- |
| `Command[R]` | Изменить состояние | ровно один                                      | ephemeral или durable |
| `Query[R]`   | Прочитать данные   | ровно один                                      | только ephemeral      |
| `Event`      | Зафиксировать факт | 0..N, каждый выполняется как отдельная операция | ephemeral или durable |

✅ Команду и запрос выполняет `Fidem.handle(message, *inputs, message_id=None)`, в ядре — `Environment.handle`, и возвращает результат обработчика. `inputs` получают только [гарды](#входы-гардов). Необъявленная команда или запрос — ошибка `MessageNotDefinedError`. Событие напрямую не выполняется и снаружи не публикуется: его публикует [обработчик](#события) команды, а обработчики события выполняет [диспетчер outbox](#диспетчер-outbox).

✅ Объявление сообщения связывает его тип с обработчиком, [мидлварями](#мидлвари-сообщений) и [режимом](#режимы-выполнения). `name` объявления — стабильное имя для сериализации и хранения, оно не зависит от имени класса. У запроса имени нет: запросы не сериализуются, а повтор объявления ловится по типу. Повторное объявление — ошибка при создании движка. У команд и [событий](#события) есть ещё `version`, по умолчанию 1. Версия команды пока нигде не хранится, 📋 она понадобится [durable-режиму](#режимы-выполнения).

📋 `schedule(name, cron, event)` публикует событие по расписанию, `unschedule(name)` снимает расписание. Расписание хранится в БД.

### Конвейер операции

✅ Операция проходит этапы в фиксированном порядке:

1. [Гарды](#гарды) обработчика и всех его мидлварей.
2. [Мидлвари сообщения](#мидлвари-сообщений), первая в списке — внешняя.
3. [Обработчик](#обработчики-сообщений).

Все три этапа — effectful-функции со свободной сигнатурой: сообщение, `MessageContext` и значения гардов подставляются по аннотациям. Гарды идут первыми, поэтому мидлварь, которая не вызывает обработчик, например кеш, не обходит проверку прав.

### Обработчики сообщений

Вид обработчика задают объявление и тип генератора. Staged-обработчик выполняет любые шаги, atomic делает ровно одну запись, query только читает.

#### Staged

✅ `@command_handler` с типом `StagedEffectful[R, E]`, в ядре — `StagedCommandDef`. Здесь `E` — события, которые публикует обработчик. Обработчик yield-ит любые эффекты, каждый эффект — отдельный шаг со своим результатом.

- **Повторы.** ✅ Ретраи после ошибки делает [мидлварь](#мидлвари-сообщений), 📋 восстановление после падения — [durable-режим](#режимы-выполнения). Повторы безопасны, потому что ID эффектов детерминированы, а записи идемпотентны.
- **Компенсаций нет.** ❓ Возможно, позже появится отдельный вид обработчика с компенсациями.

#### Atomic

✅ `@command_handler` с типом `AtomicEffectful[R, E]`, в ядре — `AtomicCommandDef`. Здесь `E` — события транзакции. Обработчик делает ровно одну запись, поэтому проблемы двойной записи, когда одна запись прошла, а другая упала, у него нет. Выполняется в две фазы:

1. Обработчик читает (`QueryEffect`) и возвращает одну запись: `ExternalWriteEffect` или вызов пишущей транзакции. Другой результат — ошибка `UnsupportedAtomicResultError`.
2. Движок выполняет запись как обычный эффект. Её ID продолжает последовательность ID чтений.

✅ Чтения выполняются вне транзакции записи. Согласованность чтения с записью обеспечивает обработчик, например условием в `UPDATE`.

#### Query

✅ `@query_handler` с типом `QueryEffectful[R]`, в ядре — `QueryDef`. Запрос выполняется как команда, которая только читает (`QueryEffect`) и возвращает результат.

### Гарды

✅ Гард аутентифицирует отправителя сообщения или проверяет его права. Гард — effectful-функция: yield-ит только `QueryEffect` и возвращает значение, а обработчик и мидлвари получают это значение параметром. Объявление — `@guard`, в ядре — `GuardDef(guard)` в `OperationEngineImpl(guard_defs=...)`.

- **Права выражаются типом значения.** Гард `admin(user: CurrentUser) -> Admin` либо возвращает `Admin`, либо бросает исключение. Поэтому обработчик с параметром `admin: Admin` выполняется только для админа.
- **Параметры** сопоставляются по [правилам DI](#di), но без скоупов. Если гарду нужен другой тип сообщения, чем обработчику, создание движка падает с ошибкой.
- **Порядок.** Каждый гард выполняется один раз на сообщение, после гардов, от которых зависит. Если гард упал, обработчик не вызывается.
- **Общие объекты**, например проверку токенов, гард получает эффектом или через замыкание. Гард без эффектов — обычная функция, её сводит к генераторной `@guard`.
- **Вложенные операции.** 📋 Вложенные запросы. 📋 У каждой операции свои значения гардов: вложенная команда и обработчик события не наследуют их от родительской операции. ❓ Откуда вложенная операция берёт [входы](#входы-гардов).

#### Входы гардов

✅ Вход — значение, которое вызывающий код передаёт в `handle` рядом с сообщением, например токен: `handle(RenameUserCommand(...), AccessToken(raw))`. Поэтому транспорт не попадает в сообщения. Вход объявляется декоратором класса `@guard_input`, в ядре — в общем списке с гардами: `guard_defs=[GuardInputDef(AccessToken), GuardDef(current_user)]`.

- **Только гарды** получают входы, как значения других гардов. Мидлвари и обработчик получают уже результат гарда, например пользователя, а не токен: их параметр с типом входа — `DependencyNotFoundError` при создании движка. Входов нет в `MessageContext` и `EffectCall`, поэтому их не видят мидлвари эффектов и обработчики эффектов. ❓ Входы для обработчиков эффектов, например чтобы пробросить токен во внешний сервис.
- **Сопоставление по типу.** Вход подходит объявлению, если он экземпляр объявленного класса. Тип, который `isinstance` не проверяет, например `NewType`, `Any` или Protocol без `@runtime_checkable`, — `UnsupportedGuardInputTypeError` при создании движка. Тип входа стоит делать своим классом: если объявить `str`, входом станет любая строка, в том числе `message_id`, по ошибке переданный позиционно.
- **Гард не перекрывает вход.** Повтор объявления входа и гард, тип значения которого совпадает с типом входа или связан с ним наследованием, — `DuplicateDependencyError` при создании движка, даже если у гарда есть имя. Иначе гард с тем же именем, что и параметр, молча подменил бы вход вызывающего кода.
- **Проверки в `handle`** выполняются до гардов. Вход необъявленного типа — `GuardInputNotDefinedError`. Вход, который подходит двум объявлениям, или два входа одного объявления — `AmbiguousGuardInputError`. Вход, который нужен гардам операции, но не передан, — `MissingGuardInputError`. Объявленный вход, который операции не нужен, игнорируется, поэтому веб-слой может передавать токен в каждый запрос одним общим кодом.
- **Обработчики событий** входов не получают: их выполняет диспетчер, и передать входы ему некому. Если гардам обработчика события нужен вход, создание движка падает с `DependencyNotFoundError`.
- **Необязательный вход** выражается значением, а не отсутствием: `AccessToken(raw=None)`, и решает гард. ❓ Параметры `X | None`.

### Мидлвари сообщений

✅ Мидлварь сообщения (`MessageMiddleware`) — effectful-функция вокруг обработчика. `yield from Proceed()` выполняет внутреннюю часть цепочки — следующую мидлварь, а после последней обработчик — и возвращает её результат. Эффекты внутренней части мидлварь не видит и может подменить только результат.

- **Эффекты.** Мидлварь yield-ит любые эффекты, кроме сообщений и чужих control-эффектов: в том числе запись и транзакции, но транзакции без событий. Правило действует и для мидлварей запроса. Тип генератора `MessageMiddlewareEffectful[R]` запрещает остальное статически.
- **`Proceed` можно не вызывать или вызывать несколько раз.** Не вызывать — для кеша, несколько раз — для ретрая. Каждый вызов запускает внутреннюю часть заново с теми же [ID](#идентификаторы-и-детерминизм) эффектов, гарды повторно не выполняются. У atomic-обработчика `Proceed` выполняет обе фазы.
- **Регистрация** — `Fidem(middlewares=...)` и `middlewares` в декораторе обработчика, в ядре — `MessageMiddlewareDef(name, middleware)`, `OperationEngineImpl(middleware_defs=...)` и `middleware_defs` объявления сообщения. Имя стабильное: от него зависят ID эффектов мидлвари. Список обработчика заменяет общий, `()` отключает мидлвари.

### События

✅ Событие объявляется `@event(name, version=1)` на классе, обработчик — `@event_handler`. В ядре — `EventDef(name, event_type, version=1, handler_defs=[...])` в `OperationEngineImpl(event_defs=...)`, обработчики вложены в объявление: `StagedEventHandlerDef(name, handler, ...)` и `AtomicEventHandlerDef(...)` с теми же настройками, что у команды. Имя обработчика уникально внутри события. Повтор события по типу или имени и повтор имени обработчика — ошибки при создании движка. Обработчики готовятся при создании движка, выполняет их [диспетчер](#диспетчер-outbox).

✅ Событие публикуется yield-ом, yield сразу возвращает `None`. События доставляются через outbox: они пишутся в БД вместе с изменениями, которые их породили, а [диспетчер](#диспетчер-outbox) рассылает их обработчикам. Так же согласуются записи в несколько систем: операция пишет в свою БД и публикует события, а во внешние системы пишут обработчики этих событий.


- **Atomic** публикует события в пишущей транзакции. Все события транзакции пишутся в outbox одним эффектом в конце этой же транзакции.
- **Staged** копит события обработчика и его транзакций в памяти и пишет их отдельной транзакцией, когда обработчик вернул результат. Запись идёт ещё внутри цепочки мидлварей, поэтому ретрай-мидлварь повторит и её, а события упавшего запуска отбрасываются. Если ephemeral-операция упала посередине, её записи в БД остаются, а события теряются. Повтор с тем же `message_id` их восстановит.
- **Гарды, запросы, читающие транзакции и мидлвари** события не публикуют. Необъявленное событие — ошибка фреймворка `EventNotDefinedError`.
- **Запись в outbox** — эффект `WriteOutboxEffect` с событиями `OutboxEvent`, у каждого события — имена его обработчиков. Обработчик эффекта и сериализацию событий даёт драйвер. Мидлвари эффектов действуют и на этот эффект. Если обработчик не зарегистрирован, первая запись падает с `EffectNotDefinedError`. ❓ Проверка на старте.

✅ Таблицу outbox создаёт секция миграций `OUTBOX_SECTION` драйвера [asyncpg](#миграции), пишет в неё и читает из неё [`AsyncpgOutbox`](#asyncpg).

- **Строка — доставка события одному обработчику**, поэтому у каждого обработчика свои статус и ретраи. `id` строки — `message_id` операции обработчика: `{ID события}:{имя обработчика}`. Повторная запись той же строки пропускается.
- **Поля строки** — ID события, `message_id` опубликовавшей его операции, имя обработчика, имя и версия события, payload в jsonb.
- **Статус** — `pending`, `done` или `failed`, и число попыток. `available_at` — когда строку можно взять: время следующей попытки, а пока строку арендовал диспетчер — конец аренды.
- **Обработанные строки** остаются для истории. ❓ Очистка старых строк.

### Диспетчер outbox

✅ Диспетчер — [сервис](#di), который в фоне забирает доставки из хранилища и выполняет каждую через `Environment.deliver(event, handler, message_id)`: гарды, мидлвари и обработчик, как у команды. Доставка at-least-once, повтор безопасен благодаря идемпотентности записи по `effect_id`. Порядок доставок не гарантируется.

- **Хранилища.** Диспетчер один (`OutboxDispatcher` в `fidem.core.outbox`), хранилищ два: таблица [PostgreSQL](#asyncpg) и [память процесса](#outbox-в-памяти). Своё хранилище — подкласс `OutboxStore`.
- **Аренда.** Диспетчер берёт доставку, засчитывает попытку и сдвигает `available_at` на срок аренды. Если диспетчер упал или не уложился в аренду, доставку после её конца берёт другой. Итог пишется, только пока доставку держит та же попытка, поэтому опоздавший диспетчер не перетирает чужой результат. Свою доставку, обработчик которой ещё работает, диспетчер не берёт повторно и после конца аренды. Если аренда последней попытки кончилась без итога, например процесс упал, доставка становится `failed` без нового запуска. 📋 Продление аренды для долгих обработчиков.
- **Известные доставки.** Диспетчер берёт только доставки событий, версий и обработчиков, объявленных в коде, поэтому при rolling deploy реплика не трогает доставки другой версии кода. Доставки удалённого обработчика остаются `pending`.
- **Ретраи.** Ошибка попытки, в том числе ошибка декодирования события, откладывает доставку по `RetryPolicy`: задержка от `initial_delay` растёт в `multiplier` раз до `max_delay`, со случайным разбросом до половины. После `max_attempts` попыток доставка `failed`. В `last_error` пишется traceback последней ошибки. ❓ Политика ретраев для отдельного обработчика.
- **Пробуждение.** Хранилище будит диспетчер, когда появляются доставки, а без уведомлений он ждёт до ближайшего `available_at`, но не дольше `poll_interval`.
- **Параллельность.** Диспетчер выполняет не больше `concurrency` доставок одновременно.
- **Остановка.** Диспетчер перестаёт брать доставки и ждёт текущие до `stop_timeout`, потом отменяет их. Отменённая доставка сразу снова доступна, её попытка не засчитывается.
- **Ошибки хранилища** диспетчер логирует и повторяет через `poll_interval`. Каждая упавшая попытка — `warning` в логе, переход в `failed` — `error`.
- **Настройки** — `OutboxDispatcherOptions(retry_policy, lease, poll_interval, concurrency, stop_timeout)`, по умолчанию 10 попыток от 1 с до 1 ч, аренда 5 мин, опрос раз в 5 с, 10 доставок, остановка 30 с.

#### Outbox в памяти

✅ `MemoryOutbox(options, *, middleware_defs=None)` в `fidem.memory` хранит доставки в памяти процесса: для тестов бизнес-логики и приложений без БД. Это [набор](#пользовательский-api): `Fidem` получает в `definitions` сам outbox, а `EnvironmentImpl` — его `effect_defs` и `dependency_defs`. Диспетчер запускается сервисом. `middleware_defs` заменяют мидлвари Environment для записи в outbox, как в `EffectDef`.

- **Отличия от PostgreSQL.** Событие хранится объектом, без сериализации, поэтому несериализуемое событие тест на памяти не поймает. Доставки не переживают процесс: при остановке `pending`-доставки и отложенные ретраи теряются.
- **Транзакции.** События транзакции попадают в хранилище, только когда транзакция закрылась без ошибки.
- **Тесты.** `await outbox.drain()` ждёт, пока не останется `pending`-доставок, включая ретраи и доставки событий, опубликованных обработчиками. `outbox.rows` — все доставки со статусом, попытками и последней ошибкой.

## Транзакции

✅ Транзакция объединяет эффекты БД. Транзакции бывают двух видов:

- **Читающая** (`ReadTransaction`) yield-ит только `DatabaseReadEffect`, чтобы читать данные из одного снимка.
- **Пишущая** (`WriteTransaction`) yield-ит любые `DatabaseEffect`, чтобы записать их атомарно.

Транзакция объявляется на уровне модуля декоратором над effectful-функцией с любыми параметрами. Вызов этой функции с аргументами — эффект, который выполняет транзакцию, как `save_user` в [примере](#пример). Читающая транзакция считается чтением, пишущая — записью, поэтому yield-ить их можно там же, где чтение и запись. Вложенные транзакции запрещены.

- **Неявная транзакция.** Эффект БД вне явной транзакции движок выполняет так, будто effectful-функция вызвала транзакцию из одного этого эффекта: `IMPLICIT_READ_TRANSACTION` для `DatabaseReadEffect`, `IMPLICIT_WRITE_TRANSACTION` для остальных эффектов БД.
- **Ядро не знает о БД.** Begin, commit и rollback делает [фабрика](#di) скоупа `TRANSACTION`. Объект транзакции служит ключом, по которому драйвер находит её настройки.
- **Откат.** Любая ошибка, в том числе ошибка коммита, и отмена откатывают транзакцию.
- **Ретраи.** Ретрай эффекта БД мидлварью эффекта повторяет его в той же транзакции, явной или неявной, но в PostgreSQL транзакция после ошибки уже сломана. Поэтому ретраить нужно операцию. ❓ Ретрай транзакции, в том числе без первой фазы atomic, savepoint-ы.

### asyncpg

✅ Драйвер PostgreSQL на asyncpg ставится extra `fidem[asyncpg]`.

`AsyncpgDatabase(pool, *, read_options, write_options, transaction_options)` — [набор](#пользовательский-api) из пула `asyncpg.Pool`, который делает фабрика приложения, и соединения из него в транзакции. Фабрика объявляется `@dependency`, поэтому автодискавери её модуля находит ту же фабрику, а не второй пул. В ядре соединение объявляет `AsyncpgConnectionDef` — зависимость `asyncpg.Connection` скоупа `TRANSACTION`, а пул — фабрика приложения. Читающая транзакция с read committed транзакцию БД не открывает: каждый запрос и так видит свой снимок. Настройки транзакций:

- `read_options` — для читающих транзакций, по умолчанию repeatable read и `READ ONLY`;
- `write_options` — для пишущих, по умолчанию read committed;
- `transaction_options` — для отдельных транзакций, по объекту транзакции. По умолчанию `IMPLICIT_READ_TRANSACTION` — read committed, поэтому одиночное чтение идёт без транзакции БД.

✅ `AsyncpgOutbox(options, *, notify=True, middleware_defs=None)` — outbox в таблице `OUTBOX_SECTION`. Это [набор](#пользовательский-api) из `effect_defs`, которые пишут события, и `dependency_defs` с сервисом [диспетчера](#диспетчер-outbox): `Fidem` получает в `definitions` сам outbox, а `EnvironmentImpl` — оба списка. Процесс, который только пишет события, например веб-реплика, передаёт `outbox.writer` с одной записью, и диспетчер у него не запускается. `middleware_defs` заменяют мидлвари Environment для записи в outbox, как в `EffectDef`. Пул и соединение объявляет `AsyncpgDatabase`, `Serializer` — приложение, например `instance(PydanticSerializer())`.

- **Запись** обрабатывает `WriteOutboxEffect`: сериализует каждое событие один раз и пишет строки одним пакетом в текущую транзакцию. Кодек события готовится при первой записи события этого типа. 📋 Готовить кодеки объявленных событий на старте.
- **NOTIFY.** С `notify=True` запись в outbox вызывает `pg_notify` в той же транзакции, и PostgreSQL будит диспетчеры после коммита. Цена — блокировка при коммите, из-за которой коммиты с уведомлениями под нагрузкой идут по очереди. Без уведомлений диспетчер находит доставки опросом.
- **Диспетчер** работает поверх `AsyncpgOutboxStore`, кодеки объявленных событий готовит на старте. Доставки берутся через `FOR UPDATE SKIP LOCKED`, поэтому диспетчеры разных процессов не мешают друг другу. Для уведомлений диспетчер держит соединение пула, поэтому пулу нужно хотя бы ещё одно соединение для запросов. Пулер в transaction mode уведомления не передаёт: такой пул должен подключаться к PostgreSQL напрямую. ❓ Отдельное соединение для уведомлений в обход пулера.

#### Миграции

✅ Системные таблицы fidem и его расширений создают и обновляют миграции. Ядро о миграциях не знает: таблицы нужны реализациям его интерфейсов в драйвере, а у реализаций без БД миграций нет. Таблицы приложения мигрирует собственный инструмент приложения.

- **Секция** `MigrationSection(name, migrations)` — миграции таблиц одного компонента, список или кортеж SQL-строк. Версия миграции — её позиция, начиная с 1. Секции независимы, у каждой свои версии. Имена секций уникальны, у секций fidem — префикс `fidem.`.
- **Запуск.** `migrate(pool, sections)` применяет неприменённые миграции секций в порядке списка. Список собирает приложение и само вызывает `migrate`, например отдельным шагом деплоя: на старте Environment миграции не применяются.
- **Хранение.** Применённые миграции и хеши их SQL хранятся в таблице `fidem.migrations`, таблицы fidem — в схеме `fidem`.
- **Транзакции.** Каждая миграция выполняется в своей транзакции: упавшая откатывается, предыдущие остаются. Параллельные вызовы ждут друг друга на advisory lock транзакции, поэтому `migrate` работает и через пулер в transaction mode.
- **Ошибки.** Если применённую миграцию изменили, `migrate` падает с `MigrationChangedError`, ничего не применив. Повтор имени секции — ошибка `DuplicateMigrationSectionError`.
- **Rolling deploy.** Версии в БД новее, чем в коде, пропускаются без ошибки, чтобы старые реплики работали с новой схемой.
- **Секции fidem:** `OUTBOX_SECTION` — [таблица outbox](#события).
- **Только вперёд**, без отката. ❓ Миграции данных функциями, миграции вне транзакции (`CREATE INDEX CONCURRENTLY`), проверка актуальности схемы на старте, CLI.

## Сериализация

✅ Сериализатор переводит значения в JSON и обратно: события — для [outbox](#события), 📋 эффекты с параметрами и результатами — для журнала durable-режима. 📋 По JSON Schema будут строиться форма отправки сообщения в дашборде и документация API.

- **Кодек.** `Serializer` готовит по типу `Codec[T]` и кеширует его. Тип любой: класс, `list[User]`, `User | None`. Какие типы поддерживаются, зависит от реализации. Неподдерживаемый тип вызывает ошибку `UnsupportedTypeError` при подготовке кодека, а не при первом использовании.
- **Форматы.** Кодек переводит значение в JSON-совместимые Python-значения (`JsonValue`) и в готовый JSON (`bytes`) и обратно. Он же строит JSON Schema 2020-12 для входных данных, вложенные типы — в `$defs`.
- **Ошибки.** Значение, которое нельзя сериализовать, — ошибка `SerializationError`. Данные, которые не подходят к типу, — ошибка `DeserializationError`, исходная ошибка библиотеки — в `__cause__`. При сериализации кодек не проверяет, что значение соответствует типу.
- **Реализации** — `PydanticSerializer` в `fidem[pydantic]` и `MsgspecSerializer` в `fidem[msgspec]`, своя реализация — подкласс `Serializer`. Строгость декодирования задаёт параметр `strict`. По умолчанию строгость как в библиотеке: pydantic приводит типы, msgspec нет.
- **Совместимость.** Реализации могут по-разному записывать одни и те же типы, например `datetime`. Если сменить сериализатор на сохранённых данных, совместимость обеспечивает приложение.
- **Границы.** Сериализатор знает только соответствие типа и JSON, а тип по имени и версии сообщения находит реестр объявлений. Сериализацией пользуется драйвер БД, а не движок и не Environment, потому что хранилищу в памяти она не нужна. Драйвер получает `Serializer` через DI.

## DI

✅ DI — внедрение зависимостей — связывает обработчики эффектов с инфраструктурой: подключением к БД, клиентом внешнего сервиса. Каждый параметр обработчика эффекта или фабрики — зависимость. Связывание автоматическое, без явных маркеров. Объявление — `@dependency`, в ядре — `EffectDependencyDef` в `EnvironmentImpl(dependency_defs=...)`.

- **Всё проверяется заранее.** При создании Environment граф зависимостей строится и проверяется целиком, включая неиспользуемые зависимости: у каждого параметра есть зависимость, выбор однозначен, циклов нет, скоупы соблюдены.
- **Сначала по типу, потом по имени.** Кандидаты — зависимости, тип которых совпадает с типом параметра или наследует его, точное совпадение не приоритетнее наследника. Если кандидат один, берётся он. Если несколько — выбирается по имени параметра, а если и так не выбрать — ошибка. Generic-тип (`Repo[User]`) совпадает только точно, но `C[Any]` равен `C`.
- **Фабрика** — асинхронная генераторная функция: до `yield` создаёт зависимость, на `yield` отдаёт её, после `yield` закрывает. В точке `yield` фабрика получает ошибку, с которой завершился скоуп, и может, например, откатить транзакцию. Объявление — `@dependency(lifetime=...)`, в ядре — `EffectDependencyDef(factory, lifetime=...)`. Готовый объект и асинхронную функцию к фабрике сводят [`instance` и `@dependency`](#пользовательский-api).
- **Скоупы** соответствуют [масштабам выполнения](#масштабы-выполнения). Скоупы вложены друг в друга: `EFFECT` в `TRANSACTION`, `TRANSACTION` в `MESSAGE`, `MESSAGE` и `SERVICE` в `APPLICATION`. Зависимость может зависеть только от зависимостей своего скоупа и скоупов вокруг него. Зависимости `APPLICATION` создаются на старте Environment параллельно по графу и закрываются на остановке. Остальные создаются лениво и последовательно, при первом эффекте своего масштаба, которому они нужны, а `EFFECT` — перед вызовом обработчика. ❓ Выбор параллельного резолва.
- **Сервисы** — зависимости скоупа `SERVICE`: фоновые задачи вроде [диспетчера outbox](#диспетчер-outbox). Они создаются после всех зависимостей `APPLICATION` по одной, в порядке объявления и после своих зависимостей, и закрываются в обратном порядке до закрытия первой зависимости `APPLICATION`. Если сервис упал на старте, Environment не стартует. Сервис зависит от `APPLICATION`, других сервисов и встроенной зависимости `Environment`, через которую выполняет сообщения. Скоуп сервисов вложен в `APPLICATION` рядом со скоупом `MESSAGE`, поэтому от сервиса и от `Environment` может зависеть только сервис, иначе создание Environment падает с `DependencyLifetimeError`. Процесс выбирает, какие сервисы запускать, составом объявлений.
- **Встроенные зависимости** — сообщение, `MessageContext`, `TransactionContext(transaction)`, эффект и `EffectContext`. Сообщение подходит только параметру типа `Message` или его подкласса, подкласс проверяется в рантайме. Зависимости скоупа `TRANSACTION` доступны только обработчикам `DatabaseEffect`, иначе создание Environment падает с `TransactionDependencyAccessError`.
- **Ошибки.** При любой ошибке закрываются все созданные зависимости, даже если какая-то из них падает при закрытии. Ошибка закрытия зависимости `EFFECT` — ошибка эффекта.
- **Ограничения.** Обработчики эффектов — только `async def`-функции. Параметры у них и у фабрик аннотированы и передаются по имени. ❓ Не защищены одновременные старты Environment и вызовы во время остановки.

## Идентификаторы и детерминизм

- ✅ **`message_id`** есть у каждого сообщения. Его можно передать в `handle`, иначе Environment генерирует случайный UUID. `MessageContext` создаёт только Environment.
- ✅ **ID эффектов** детерминированно выводятся из `message_id` и порядкового номера эффекта. У каждого гарда и каждой мидлвари сообщения свой поток ID: он выводится из имени мидлвари или из имени и типа значения гарда. Поэтому гарды и мидлвари можно добавлять и менять, не сдвигая ID обработчика. Эффекты транзакции продолжают поток того, кто её yield-ит.
- **Порождённое операцией** тоже получает детерминированные ID, и так далее по цепочке. ✅ ID события — ID эффекта на месте его yield. 📋 Вложенные сообщения.
- 📋 **Идемпотентность на входе.** Повторная команда с тем же `message_id` возвращает сохранённый результат. Включается настройкой команды и работает в любом режиме.
- 📋 **Идемпотентность на выходе.** `effect_id` передаётся во внешние системы как ключ идемпотентности.
- 📋 **`correlation_id` и `causation_id`** связывают всю цепочку сообщений в логах и трассировке.

## Режимы выполнения

Режим (`execution_mode`) определяет, переживёт ли прогресс операции падение процесса. Восстанавливать есть смысл только операцию с несколькими записями, поэтому запрос и 📋 atomic-команда всегда ephemeral.

- ✅ **Ephemeral.** Прогресс хранится только в памяти и теряется при падении процесса.
- 📋 **Durable.** Сообщение и каждый шаг операции — эффект с параметрами и результатом — записываются в журнал операции в БД.
  - Журнал один на всю цепочку, у каждой записи указан источник: гард, мидлварь или обработчик. `Proceed` — тоже шаг, у каждой попытки внутренней части свой раздел журнала.
  - При старте Environment подхватывает незавершённые операции. Он проигрывает всю цепочку, включая гарды, на сохранённых результатах до точки остановки и продолжает выполнение.
  - Журнал копится в памяти и сбрасывается в БД перед первой записью: до неё операцию безопасно выполнить с нуля.
  - В журнале сохраняется состав цепочки с именами и версиями мидлварей, чтобы восстановление шло тем же кодом.
  - ❓ Как журналировать транзакции и сериализовать их аргументы.
  - ❓ Распределение работы: один универсальный тип воркера или специализированные.

📋 Команды разных режимов можно вызывать друг из друга. ❓ Правила сочетания режимов и видов обработчиков.

## Архитектура

**Ядро минималистично.** В ядре только то, что нельзя сделать вне его. Ретраи, кеши, идемпотентность и подобное — мидлвари и хелперы, а частные случаи сводятся к общей форме вне ядра.

Ядро состоит из двух частей: движок решает, что делать, а Environment делает.

- ✅ **Движок операций** (`OperationEngine`) — чистый код без ввода-вывода. Он запускает конвейер операции и превращает поток эффектов в поток **инструкций** для Environment — план выполнения `ExecutionPlan`, тоже генератор. Движок решает всё, что касается выполнения: режимы, транзакции, журнал, публикацию событий, control-эффекты. Сложная логика собрана в движке, потому что чистый код проще всего тестировать: тест проверяет поток инструкций без моков ввода-вывода.
- ✅ **Environment** исполняет инструкции и своей логики выполнения не содержит, поэтому окружений может быть несколько, например тестовое. Запускается и останавливается через `async with environment:`, вызов вне этого блока — ошибка. Environment владеет обработчиками эффектов и зависимостями и запускает [сервисы](#di): outbox-диспетчер и 📋 планировщик.

Инструкции:

- ✅ `CallEffectHandlerInstruction` — вызвать обработчик эффекта.
- ✅ `RunTransactionInstruction` — выполнить вложенный план в скоупе `TRANSACTION` и вернуть его результат.
- 📋 Записать в журнал.

Запись в outbox — не инструкция, а обычный эффект БД `WriteOutboxEffect`, который выдаёт движок.

Команда выполняется так, запрос — так же:

1. Вызывающий код передаёт команду в `Environment.handle`.
2. Environment получает у движка план выполнения: `OperationEngine.handle(message, message_context, inputs)`.
3. Environment исполняет каждую инструкцию плана и отправляет результат обратно в план, движок передаёт его в effectful-функцию.
4. Когда обработчик возвращает результат, план завершается, и Environment возвращает результат вызывающему коду.

✅ **API разделён на два слоя.** Корень `fidem` — API приложения: сообщения, категории эффектов, типы генераторов, транзакции, `Proceed`, контексты, эффекты stdlib, настройки диспетчера outbox, `Error` и ошибки, которые ловят во время работы. Ошибки объявлений пользовательского API — в `fidem.errors`. Сюда же входят [пользовательский API](#пользовательский-api) — декораторы и класс `Fidem`. `fidem.core` — внутренний API, на котором строится API приложения: объявления (`StagedCommandDef`, `EffectDef` и т. п.), `EnvironmentImpl`, движок и ошибки объявлений. Ядро лежит в пакете `fidem/core/` и не импортирует ничего из `fidem` вне него, это проверяет тест.

✅ **Импорт — из корня слоя:** `from fidem import Command`, `from fidem.core import EnvironmentImpl`. Модули реализации можно перестраивать: корни сохраняют имена. Драйверы и сериализаторы импортируются из своих модулей (`fidem.asyncpg`, `fidem.memory`, `fidem.pydantic`, `fidem.msgspec`), поэтому `import fidem` не требует extras. Корень драйвера тоже даёт только API приложения, а внутреннее, например `AsyncpgOutboxStore`, остаётся в его модулях.

✅ **Ошибки** fidem наследуют `fidem.Error`, поэтому любую ошибку фреймворка можно поймать одним `except`. `ValueError` и `TypeError` из fidem означают ошибку в самом fidem.

- **Дашборд** — полная картина приложения:
  - какие есть сообщения и как они выполняются;
  - граф сообщений, построенный по типам: команда → события, которые она порождает → их события и так далее, и его проверка при старте.
- **Manhole** — подключение к работающему приложению: Python REPL в контексте Environment. Из него можно отправить команду, запрос или событие и выполнить другие действия фреймворка. Дашборд показывает, что происходит в приложении, а manhole позволяет в нём действовать. ❓ Доступ и защита подключения.
- **Наблюдаемость** без ручной настройки: логи с `correlation_id` и `causation_id`, метрики и трассировка по сообщениям и эффектам.
- **Надёжность:** outbox, durable-выполнение, ретраи, идемпотентность на входе и на выходе.
- **Кеши:** движок знает, какие эффекты выполняются, поэтому сам ставит и инвалидирует кеши.
- **Тестирование:** бизнес-логика проверяется как поток эффектов, без моков.
