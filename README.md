Фреймворк для бизнес-логики на основе системы эффектов. Бизнес-логика не выполняет побочные эффекты сама, а описывает их: обработчик сообщения — генератор, который yield-ит описания действий и получает обратно их результаты. Исполняет действия фреймворк.

Поэтому фреймворк знает о приложении почти всё: статически — какие есть сообщения и обработчики, кто кого вызывает и что каждому обработчику разрешено делать; в рантайме — каждое выполненное действие, его результат и длительность. На этом знании он сам даёт то, что обычно пишут вручную в каждом обработчике: outbox, durable-выполнение, ретраи, идемпотентность, логи, метрики, трассировку и [другое](#что-даёт-эта-конструкция).

Этот документ — единый источник истины о том, как устроен фреймворк. Статусы:

- ✅ реализовано;
- 📋 запланировано;
- ❓ надо продумать.

Почему решения приняты именно так — в [записях о решениях](docs/decisions/README.md).

## Пример

```python
async def pool() -> AsyncGenerator[Pool]:
    async with create_pool(DATABASE_URL) as pool:
        yield pool


@dataclass(frozen=True, slots=True)
class GetUserEffect(DatabaseReadEffect[User]):
    user_id: str


async def handle_get_user(connection: Connection, effect: GetUserEffect) -> User: ...


@dataclass(frozen=True, slots=True)
class SaveUserEffect(DatabaseWriteEffect[User]):
    user: User


async def handle_save_user(connection: Connection, effect: SaveUserEffect) -> User: ...


@dataclass(frozen=True, slots=True)
class RenameUserCommand(Command[User]):
    user_id: str
    name: str


@dataclass(frozen=True, slots=True)
class GetUserQuery(Query[User]):
    user_id: str


@WriteTransaction
def save_user(user: User) -> WriteTransactionEffectful[User]:
    return (yield from SaveUserEffect(user))


def rename_user(command: RenameUserCommand) -> AtomicEffectful[User]:
    user = yield from GetUserEffect(command.user_id)
    return save_user(replace(user, name=command.name))


def get_user(query: GetUserQuery) -> QueryEffectful[User]:
    return (yield from GetUserEffect(query.user_id))


environment = EnvironmentImpl(
    operation_engine=OperationEngineImpl(
        command_defs=[AtomicCommandDef("rename_user", RenameUserCommand, rename_user)],
        query_defs=[QueryDef("get_user", GetUserQuery, get_user)],
    ),
    effect_defs=[
        EffectDef(GetUserEffect, handle_get_user),
        EffectDef(SaveUserEffect, handle_save_user),
    ],
    dependency_defs=[EffectDependencyDef(pool), AsyncpgConnectionDef()],
)
async with environment:
    user = await environment.execute(RenameUserCommand("u1", "Alice"), message_id="request-42")
    user = await environment.query(GetUserQuery("u1"))
```

Полные примеры: [`examples/01_ephemeral_command.py`](examples/01_ephemeral_command.py), [`examples/02_dependencies.py`](examples/02_dependencies.py), [`examples/03_guards.py`](examples/03_guards.py), [`examples/04_effect_middlewares.py`](examples/04_effect_middlewares.py), [`examples/05_message_middlewares.py`](examples/05_message_middlewares.py), [`examples/06_atomic_commands.py`](examples/06_atomic_commands.py), [`examples/07_queries.py`](examples/07_queries.py).

## Модель

**Effectful-функция** — синхронная генераторная функция `Effectful[R, E]`: yield-ит эффекты типа `E`, на каждый получает результат в той же точке кода и возвращает `R`. Тип эффектов — часть сигнатуры, поэтому то, что функции разрешено делать, видно и проверяется статически. ✅ В этой форме пишутся обработчики сообщений, [гарды](#гарды), [мидлвари сообщений](#мидлвари-сообщений) и [транзакции](#транзакции).

**Контракт детерминизма.** Effectful-функция не делает ввода-вывода и не читает время, случайность и глобальное состояние напрямую — только через эффекты. При тех же входных данных и результатах эффектов она yield-ит ту же последовательность эффектов. На этом держатся ретраи, восстановление и воспроизводимость. Сейчас контракт не проверяется. 📋 По возможности ловить попытки его нарушить.

**Типы защищают от ошибок.** Тип effectful-функции по возможности запрещает некорректные сочетания эффектов. ✅ В рантайме недопустимый эффект — ошибка `UnsupportedEffectError`.

✅ **Ошибки**

- Ошибка эффекта пробрасывается в effectful-функцию (`generator.throw`) в точке `yield from`, её можно поймать и продолжить. У составного эффекта — транзакции, `Proceed` — ошибка это непойманная ошибка его внутренней части. Непойманная ошибка обработчика завершает операцию и выходит из `Environment.execute`.
- Ошибки самого фреймворка, например недопустимый эффект, в effectful-функцию не пробрасываются.
- Если выполнение прервано (отмена, закрытие плана), генераторы закрываются сразу, поэтому их `finally` и `with` отрабатывают.

### Масштабы выполнения

✅ Работа приложения делится на вложенные масштабы: операция порождает одну или несколько транзакций, транзакция — один или несколько эффектов. Эффекты БД всегда выполняются в [транзакции](#транзакции), остальные — прямо в операции.

| Масштаб    | Что это                                                  | Что даёт                                                                  | Скоуп DI      |
| ---------- | -------------------------------------------------------- | ------------------------------------------------------------------------- | ------------- |
| Приложение | работа Environment                                       | общие ресурсы: пул соединений, клиенты                                    | `APPLICATION` |
| Операция   | обработка одного сообщения: гарды, мидлвари и обработчик | ✅ ретраи, 📋 восстановление после падения, 📋 идемпотентность на входе     | `MESSAGE`     |
| Транзакция | эффекты БД в одной транзакции                            | ✅ согласованность, 📋 события в outbox той же транзакцией                 | `TRANSACTION` |
| Эффект     | одно действие                                            | ✅ идемпотентность записи по `effect_id`                                   | `EFFECT`      |

## Эффекты

✅ Эффект — неизменяемое описание действия. Параметр типа — тип результата.

| Категория        | Что это                                                                                                       | Исполняет   |
| ---------------- | ------------------------------------------------------------------------------------------------------------- | ----------- |
| `InternalEffect` | Действие внутри процесса без внешних побочных эффектов: кеш, конфиг, случайные числа, обычный `asyncio.sleep` | Environment |
| `ExternalEffect` | Обращение к внешней системе: HTTP, брокер                                                                     | Environment |
| `DatabaseEffect` | Работа с собственной БД сервиса                                                                               | Environment |
| `ControlEffect`  | Управление выполнением: `Proceed`, [транзакции](#транзакции), 📋 параллельный запуск эффектов                  | Движок      |

Внешние и БД-эффекты делятся на чтение и запись: `ExternalReadEffect`, `ExternalWriteEffect`, `DatabaseReadEffect`, `DatabaseWriteEffect`. Запись меняет состояние, поэтому её обработчик должен быть идемпотентен по `effect_id`: при ретрае и восстановлении операции запись повторяется с тем же ID.

**Только чтение** — `QueryEffect`: `InternalEffect`, `ExternalReadEffect`, `DatabaseReadEffect` и читающие транзакции. Чтение безопасно повторять.

✅ **Обработчик эффекта** — асинхронная функция, регистрируется через `EffectDef(effect_type, handler)`. На тип эффекта — ровно один обработчик, тип ищется точно, без учёта наследования. Сигнатура свободная: все параметры, включая сам эффект и `EffectContext`, подставляются через [DI](#di).

### Мидлвари эффектов

✅ Эффекты, которые исполняет Environment, проходят мидлвари эффекта, затем DI и обработчик. Control-эффекты исполняет движок, мидлвари действуют на эффекты внутри них.

Мидлварь эффекта (`EffectMiddleware`) — асинхронная функция `middleware(effect_call, call_next)`. `EffectCall` содержит сообщение, эффект и их контексты, мидлварь их только читает. `call_next()` вызывает следующую мидлварь, а после последней — обработчик эффекта.

- Мидлвари работают до DI, поэтому каждый вызов `call_next` получает новые зависимости скоупа `EFFECT` и новую [неявную транзакцию](#транзакции), а ошибки резолва и закрытия видит как свои.
- Может не вызвать `call_next` (кеш, заглушка) или вызвать несколько раз (ретрай), в том числе одновременно. `call_next` после завершения сообщения — ошибка `ScopeClosedError`.
- Ошибка мидлвари — ошибка эффекта.
- Регистрация — `EffectMiddlewareDef(middleware)`. Общий список — `EnvironmentImpl(effect_middleware_defs=...)`, список в `EffectDef(..., middleware_defs=...)` заменяет его, `()` — без мидлварей. Первая в списке — внешняя.
- Зависимости мидлварь получает через замыкание. ❓ Доступ к зависимостям `APPLICATION`.

## Сообщения

✅ Сообщение — вход в бизнес-логику и тоже эффект. 📋 Поэтому обработчик сможет вызывать команды и запросы и публиковать события так же, как выполняет любой эффект. ❓ Семантика вложенных команд, особенно в staged-обработчиках.

| Тип          | Назначение         | Обработчиков на тип                             | Режим                 | Вызов                   |
| ------------ | ------------------ | ----------------------------------------------- | --------------------- | ----------------------- |
| `Command[R]` | Изменить состояние | ровно один                                      | ephemeral или durable | ✅ `Environment.execute` |
| `Query[R]`   | Прочитать данные   | ровно один                                      | только ephemeral      | ✅ `Environment.query`   |
| `Event`      | Зафиксировать факт | 0..N, каждый выполняется как отдельная операция | ephemeral или durable | 📋 `Environment.publish` |

✅ Объявление связывает тип сообщения с обработчиком, [мидлварями](#мидлвари-сообщений) и [режимом](#режимы-выполнения). Его `name` — стабильное имя для сериализации и хранения, не зависящее от имени класса. Повторное объявление и необъявленное сообщение — ошибки. 📋 Ещё будет `version`. 📋 Объявления событий.

📋 `schedule(name, cron, event)` публикует событие по расписанию, `unschedule(name)` снимает его. Расписание хранится в БД.

### Конвейер операции

✅ Операция проходит этапы в фиксированном порядке:

1. [Гарды](#гарды) обработчика и всех его мидлварей.
2. [Мидлвари сообщения](#мидлвари-сообщений), первая в списке — внешняя.
3. [Обработчик](#обработчики-сообщений).

Все три — effectful-функции со свободной сигнатурой: сообщение, `MessageContext` и значения гардов подставляются по аннотациям. Гарды стоят первыми, поэтому мидлварь, которая не вызывает обработчик, например кеш, не обходит проверку прав.

### Обработчики сообщений

Вид обработчика задаётся объявлением и типом генератора.

#### Staged

✅ `StagedCommandDef`, `StagedEffectful[R, E]`, где `E` — события, которые он публикует. Yield-ит любые эффекты, каждый эффект — отдельный шаг со своим результатом.

- ✅ Ретраи после ошибки — [мидлварью](#мидлвари-сообщений), 📋 восстановление после падения — в [durable-режиме](#режимы-выполнения). Повторы безопасны благодаря детерминированным ID и идемпотентным записям.
- Компенсаций нет. ❓ Возможно, позже появится отдельный вид обработчика с компенсациями.

#### Atomic

✅ `AtomicCommandDef`, `AtomicEffectful[R, E]`, где `E` — события транзакции. Делает ровно одну запись, поэтому проблемы двойной записи у него нет. Выполняется в две фазы:

1. Обработчик читает (`QueryEffect`) и возвращает одну запись: `ExternalWriteEffect` или вызов пишущей транзакции. Другой результат — ошибка `UnsupportedAtomicResultError`.
2. Движок выполняет запись как обычный эффект. Её ID продолжают последовательность чтений.

✅ Чтения выполняются вне транзакции записи. Согласованность чтения с записью — забота обработчика, например условие в `UPDATE`.

#### Query

✅ `QueryDef`, `QueryEffectful[R]`. Запрос выполняется как команда, которая только читает (`QueryEffect`) и возвращает результат.

### Гарды

✅ Гард аутентифицирует отправителя сообщения или проверяет его права. Это effectful-функция, которая yield-ит только `QueryEffect` и возвращает значение. Обработчик и мидлвари получают это значение параметром. Регистрация — `GuardDef(guard)` в `OperationEngineImpl(guard_defs=...)`.

- Проверка прав выражается типом значения: гард `admin(user: CurrentUser) -> Admin` либо возвращает `Admin`, либо бросает исключение, поэтому обработчик с параметром `admin: Admin` выполняется только для админа.
- Параметры сопоставляются по [правилам DI](#di), без скоупов. Если гарду нужен другой тип сообщения, чем у обработчика, — ошибка при создании движка.
- Каждый гард выполняется один раз на сообщение, после гардов, от которых зависит. Если гард упал, обработчик не вызывается.
- Общие объекты, например проверку токенов, гард получает через замыкание. 📋 Хелперы вне ядра сведут к гарду частные случаи, например обычную функцию.
- 📋 Вложенные запросы. 📋 У каждой операции свои значения гардов: вложенная команда и обработчик события не наследуют их от родительской операции.

### Мидлвари сообщений

✅ Мидлварь сообщения (`MessageMiddleware`) — effectful-функция. `yield from Proceed()` выполняет внутреннюю часть цепочки (следующую мидлварь, а после последней — обработчик) и возвращает её результат. Эффекты внутренней части мидлварь не видит, подменить может только результат.

- Yield-ит любые эффекты, кроме сообщений и чужих control-эффектов, в том числе запись и транзакции. Это касается и мидлварей запроса.
- Может не вызвать `Proceed` (кеш) или вызвать несколько раз (ретрай). Каждый вызов запускает внутреннюю часть заново с теми же [ID](#идентификаторы-и-детерминизм) эффектов, гарды не перезапускаются. У atomic `Proceed` выполняет обе фазы.
- Регистрация — `MessageMiddlewareDef(name, middleware)`, имя стабильное. Общий список — `OperationEngineImpl(middleware_defs=...)`, список в объявлении сообщения заменяет его, `()` — без мидлварей. Настройки — через замыкание.

### События

📋 События доставляются через outbox: пишущая транзакция yield-ит события, они пишутся в outbox той же транзакцией, а `run_outbox_dispatcher` рассылает их обработчикам после успешного завершения операции. Несколько записей в разные системы согласуются так же: операция пишет в свою БД и публикует события, а во внешние системы пишут обработчики этих событий.

✅ Таблица outbox — секция миграций `OUTBOX_SECTION` в [asyncpg](#миграции), 📋 запись в неё и диспетчер.

- Строка — доставка события одному обработчику, поэтому у каждого обработчика свои статус и ретраи. `id` строки — `message_id` операции обработчика, выведенный из ID события и имени обработчика.
- В строке — ID события, `message_id` операции, которая его опубликовала, имя обработчика, имя и версия события, payload в jsonb.
- Статус `pending`, `done` или `failed`, число попыток. `available_at` — когда строку можно взять: время следующей попытки, а при аренде диспетчером — конец аренды.
- Обработанные строки остаются для истории. ❓ Очистка старых строк.

📋 События staged-обработчика копятся в памяти и публикуются после успешного завершения операции. ❓ Вариант: события его транзакций сразу пишутся в outbox с пометкой, что операция не завершилась, и после её успешного завершения помечаются готовыми к обработке.

## Транзакции

✅ Транзакция объединяет эффекты БД: читающая (`ReadTransaction`) yield-ит только `DatabaseReadEffect`, чтобы прочитать данные из одного снимка, пишущая (`WriteTransaction`) — любые `DatabaseEffect`, чтобы записать атомарно. Вложенная транзакция запрещена. Транзакция объявляется на уровне модуля декоратором над effectful-функцией с любыми параметрами, вызов с аргументами — эффект, который её выполняет (см. `save_user` в [примере](#пример)). Читающая транзакция — чтение, пишущая — запись, поэтому yield-ить их можно там же, где чтение и запись.

- **Неявная транзакция** — у эффекта БД вне явной: на один вызов обработчика эффекта.
- Ядро не знает о БД: begin, commit и rollback делает [фабрика](#di) скоупа `TRANSACTION`. Объект транзакции — ключ, по которому драйвер находит её настройки.
- Ошибка, в том числе ошибка коммита, и отмена откатывают транзакцию.
- Ретрай отдельного эффекта внутри явной транзакции повторяет его в той же транзакции, а в PostgreSQL она после ошибки уже сломана. Ретраить надо операцию. ❓ Ретрай транзакции, в том числе без первой фазы atomic, savepoint-ы.

### asyncpg

✅ `fidem[asyncpg]`. `AsyncpgConnectionDef` объявляет зависимость `asyncpg.Connection` скоупа `TRANSACTION` из пула `asyncpg.Pool`, который приложение объявляет своей фабрикой. Настройки: `read_options` для читающих транзакций (по умолчанию repeatable read, `READ ONLY`), `write_options` для пишущих (по умолчанию read committed) и `transaction_options` для отдельных транзакций по объекту транзакции. Неявное чтение транзакцию не открывает.

#### Миграции

✅ Системные таблицы fidem и его расширений создаются и обновляются миграциями. Ядро о миграциях не знает: таблицы нужны реализациям его интерфейсов в драйвере, у реализаций без БД миграций нет. Таблицы приложения мигрирует его собственный инструмент.

- `MigrationSection(name, migrations)` — миграции таблиц одного компонента: список или кортеж SQL-строк, версия миграции — её позиция начиная с 1. Секции независимы, у каждой свои версии. Имена секций уникальны, у секций fidem — префикс `fidem.`.
- `migrate(pool, sections)` применяет неприменённые миграции секций в порядке списка. Список собирает приложение и вызывает `migrate` само, например отдельным шагом деплоя: на старте Environment миграции не применяются.
- Применённые миграции и хеши их SQL хранятся в `fidem.migrations`, таблицы fidem — в схеме `fidem`.
- Каждая миграция — в своей транзакции: упавшая откатывается, предыдущие остаются. Параллельные вызовы ждут друг друга на advisory lock транзакции, поэтому `migrate` работает и через пулер в transaction mode.
- Изменённая применённая миграция — ошибка `MigrationChangedError` до применения чего-либо. Повтор имени секции — `DuplicateMigrationSectionError`.
- Версии в БД новее, чем в коде, пропускаются без ошибки, чтобы при rolling deploy старые реплики работали с новой схемой.
- Секции fidem: `OUTBOX_SECTION` — [таблица outbox](#события).
- Только вперёд, без отката. ❓ Миграции данных функциями, миграции вне транзакции (`CREATE INDEX CONCURRENTLY`), проверка актуальности схемы на старте, CLI.

## DI

✅ DI связывает обработчики эффектов с инфраструктурой: подключением к БД, клиентом внешнего сервиса. Каждый параметр обработчика эффекта или фабрики — зависимость, связывание автоматическое, без явных маркеров. Регистрация — `EnvironmentImpl(dependency_defs=...)`.

- **Всё готовится заранее.** При создании Environment граф зависимостей строится и проверяется целиком, включая неиспользуемые зависимости: каждому параметру есть зависимость, выбор однозначен, циклов нет, скоупы соблюдены.
- **Сначала по типу, потом по имени.** Кандидаты — зависимости, тип которых совпадает с типом параметра или наследует его, точное совпадение не приоритетнее. Один кандидат — берём его, несколько — выбираем по имени параметра, иначе ошибка. Generic-тип (`Repo[User]`) совпадает только точно, но `C[Any]` равен `C`.
- **Фабрика** — асинхронная генераторная функция: до `yield` создаёт зависимость, `yield` отдаёт её, после `yield` закрывает. В точке `yield` фабрика получает ошибку, с которой завершился скоуп, и может, например, откатить транзакцию. Регистрация — `EffectDependencyDef(factory, lifetime=...)`. 📋 Готовый объект и асинхронную функцию сведут к фабрике хелперы вне ядра.
- **Скоупы** — по [масштабам выполнения](#масштабы-выполнения). Зависимость может зависеть только от зависимостей того же или более широкого скоупа. `APPLICATION` создаются на старте Environment параллельно по графу и закрываются на остановке. Остальные создаются лениво, при первом эффекте своего масштаба, которому нужны, `EFFECT` — перед вызовом обработчика, и резолвятся последовательно. ❓ Выбор параллельного резолва.
- **Встроенные зависимости** — сообщение, `MessageContext`, `TransactionContext(read_only, transaction)`, эффект и `EffectContext`. Сообщение подходит только параметру типа `Message` или его подкласса, подкласс проверяется в рантайме. Зависимости скоупа `TRANSACTION` доступны только обработчикам `DatabaseEffect`, иначе ошибка `TransactionDependencyAccessError` при создании Environment.
- **Ошибки.** При любой ошибке созданные зависимости закрываются, все, даже если какая-то падает при закрытии. Ошибка закрытия зависимости `EFFECT` — ошибка эффекта.

**Ограничения:** обработчики эффектов — только `async def`-функции, параметры у них и у фабрик аннотированы и передаются по имени. ❓ Не защищены одновременные старты Environment и вызовы во время остановки.

## Идентификаторы и детерминизм

- ✅ У каждого сообщения есть `message_id`: его можно передать в `execute` и `query`, иначе Environment генерирует случайный UUID. `MessageContext` создаёт только Environment.
- ✅ ID эффектов детерминированно выводятся из `message_id` и порядкового номера эффекта. У каждого гарда и каждой мидлвари сообщения свой поток ID, выведенный из имени мидлвари или из имени и типа значения гарда, поэтому их добавление и изменение не сдвигает ID обработчика. Эффекты транзакции продолжают поток того, кто её yield-ит.
- 📋 Всё, что порождает операция (события, вложенные сообщения), тоже получает детерминированные ID, и так далее по цепочке.
- 📋 Идемпотентность на входе: повторная команда с тем же `message_id` возвращает сохранённый результат. Включается настройкой команды и работает в любом режиме.
- 📋 Идемпотентность на выходе: `effect_id` передаётся во внешние системы как ключ идемпотентности.
- 📋 `correlation_id` и `causation_id` связывают всю цепочку сообщений в логах и трассировке.

## Режимы выполнения

Режим (`execution_mode`) определяет, переживает ли прогресс операции падение процесса. Восстанавливать есть что только у операции с несколькими записями, поэтому запрос и 📋 atomic-команда всегда ephemeral.

- ✅ **Ephemeral.** Прогресс хранится только в памяти и при падении процесса теряется.
- 📋 **Durable.** Сообщение и каждый шаг операции (эффект с параметрами и результатом) записываются в журнал операции в БД.
  - Журнал один на всю цепочку, у каждой записи указан источник: гард, мидлварь или обработчик. `Proceed` — тоже шаг, у каждой попытки внутренней части свой раздел.
  - При старте Environment подхватывает незавершённые операции. Вся цепочка, включая гарды, проигрывается на сохранённых результатах до точки остановки и продолжает выполнение.
  - Журнал копится в памяти и сбрасывается в БД перед первой записью: до неё операцию можно безопасно выполнить с нуля.
  - В журнале сохраняется состав цепочки с именами и версиями мидлварей, чтобы восстановление шло тем же кодом.
  - ❓ Как журналировать транзакции и сериализовать их аргументы. Где открывать неявную транзакцию, чтобы запись эффекта и запись журнала шли одной транзакцией.
  - ❓ Распределение работы: один универсальный тип воркера или специализированные.

📋 Команды разных режимов можно вызывать друг из друга. ❓ Правила сочетания режимов и видов обработчиков.

## Архитектура

**Минималистичное ядро.** В ядре только то, что нельзя сделать вне его. Ретраи, кеши, идемпотентность и подобное — мидлвари и хелперы, а частные случаи сводятся к общей форме вне ядра.

Ядро состоит из двух частей:

- ✅ **Движок операций** (`OperationEngine`) чистый, без ввода-вывода. Он запускает конвейер операции и превращает поток эффектов в поток **инструкций** для Environment (`ExecutionPlan`, тоже генератор). Он же решает всё, что касается выполнения: режимы, транзакции, журнал, публикацию событий, control-эффекты. Сложная логика сосредоточена здесь, потому что чистый код проще всего тестировать: проверяется поток инструкций без моков ввода-вывода.
- ✅ **Environment** исполняет инструкции и своей логики выполнения не содержит, поэтому окружений может быть несколько, например тестовое. Запускается и останавливается через `async with environment:`, вызовы вне этого блока — ошибка. Владеет обработчиками эффектов и зависимостями, 📋 outbox-диспетчером и планировщиком.

Инструкции:

- ✅ `CallEffectHandlerInstruction` — вызвать обработчик эффекта.
- ✅ `RunTransactionInstruction` — выполнить вложенный план в скоупе `TRANSACTION` и вернуть его результат.
- 📋 Записать в журнал, записать в outbox.

Как выполняется команда (запрос — так же):

1. Вызывающий код передаёт команду в `Environment.execute`.
2. Environment получает у движка план выполнения: `OperationEngine.execute(command, message_context)`.
3. Environment исполняет каждую инструкцию плана и отправляет результат обратно в план, движок передаёт его в effectful-функцию.
4. Когда обработчик возвращает результат, план завершается, и Environment возвращает результат вызывающему коду.

## Что даёт эта конструкция

📋 На знании о сообщениях и эффектах строится:

- **Дашборд** — полная картина приложения:
  - какие есть сообщения и как они выполняются;
  - граф сообщений, построенный по типам: команда → события, которые она порождает → их события и т.д., и его проверка при старте.
- **Manhole** — подключение к работающему приложению: Python REPL в контексте Environment, из которого можно отправить команду, запрос или событие и выполнить другие действия фреймворка. Дашборд показывает, что происходит в приложении, manhole позволяет в нём действовать. ❓ Доступ и защита подключения.
- **Наблюдаемость** без ручной настройки: логи с `correlation_id`/`causation_id`, метрики и трассировка по сообщениям и эффектам.
- **Надёжность:** outbox, durable-выполнение, ретраи, идемпотентность на входе и на выходе.
- **Кеши:** движок знает, какие эффекты выполняются, поэтому сам ставит и инвалидирует кеши.
- **Тестирование:** бизнес-логика проверяется как поток эффектов, без моков.

Список не исчерпывающий: всё, что можно извлечь из знания о сообщениях и эффектах, — потенциальная возможность фреймворка.
