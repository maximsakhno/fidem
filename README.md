# fidem

[![CI](https://github.com/maximsakhno/fidem/actions/workflows/ci.yml/badge.svg)](https://github.com/maximsakhno/fidem/actions/workflows/ci.yml)
[![codecov](https://codecov.io/gh/maximsakhno/fidem/graph/badge.svg)](https://codecov.io/gh/maximsakhno/fidem)

Фреймворк для бизнес-логики на основе системы эффектов. Обработчик сообщения — генератор: он не выполняет побочные эффекты сам, а yield-ит их описания и получает обратно результаты. Фреймворк знает каждое действие приложения, и за счёт этого даёт из коробки outbox, durable-выполнение, идемпотентность, ретраи, кеши, логи, метрики, трассировку и дашборд.

Этот документ — единый источник истины о том, как устроен фреймворк. Статусы:

- ✅ реализовано;
- 📋 запланировано;
- ❓ надо продумать.

## Пример

```python
@dataclass(frozen=True, slots=True)
class GetUserEffect(DatabaseReadEffect[User]):
    user_id: str


async def handle_get_user(context: EffectContext, effect: GetUserEffect) -> User: ...


@dataclass(frozen=True, slots=True)
class SaveUserEffect(DatabaseWriteEffect[User]):
    user: User


async def handle_save_user(context: EffectContext, effect: SaveUserEffect) -> User: ...


@dataclass(frozen=True, slots=True)
class RenameUserCommand(Command[User]):
    user_id: str
    name: str


def rename_user(context: MessageContext, command: RenameUserCommand) -> Effectful[User, Effect[Any]]:
    user = yield from GetUserEffect(command.user_id)
    return (yield from SaveUserEffect(replace(user, name=command.name)))


environment = EnvironmentImpl(
    operation_engine=OperationEngineImpl(
        command_defs=[StagedCommandDef("rename_user", RenameUserCommand, rename_user)],
    ),
    effect_defs=[
        EffectDef(GetUserEffect, handle_get_user),
        EffectDef(SaveUserEffect, handle_save_user),
    ],
)
user = await environment.execute(RenameUserCommand("u1", "Alice"), message_id="request-42")
```

Полный пример: [`examples/01_ephemeral_command.py`](examples/01_ephemeral_command.py).

## Эффекты

✅ Эффект — неизменяемый объект, который описывает действие. Параметр типа — тип результата. `yield from effect` отдаёт эффект исполнителю и возвращает его результат.

Категория определяет, кто и как исполняет эффект:

| Категория | Что это | Исполняет |
|---|---|---|
| `InternalEffect` | Действие внутри процесса без внешних побочных эффектов: кеш, конфиг, случайные числа, обычный `asyncio.sleep` | Environment |
| `ExternalEffect` | Обращение к внешней системе: HTTP, брокер | Environment |
| `DatabaseEffect` | Работа с собственной БД сервиса. Выделена отдельно, потому что на ней строятся outbox и durable-режим | Environment |
| `ControlEffect` | Управление выполнением: например, параллельный запуск нескольких эффектов или возврат зависимости из DI-фабрики | Движок 📋 |

Внешние и БД-эффекты делятся на чтение и запись: `ExternalReadEffect`, `ExternalWriteEffect`, `DatabaseReadEffect`, `DatabaseWriteEffect`.

- **Чтение** можно безопасно повторять.
- **Запись** меняет состояние. Её обработчик должен быть идемпотентен по `effect_id`: при ретрае и при восстановлении операции запись повторяется с тем же ID.

### Обработчики эффектов

- ✅ Обработчик эффекта — асинхронная функция. Регистрируется в Environment через `EffectDef(effect_type, handler)`.
- ✅ На каждый тип эффекта — ровно один обработчик. Тип ищется точно, без учёта наследования.
- ✅ Сейчас сигнатура фиксирована: `handler(context: EffectContext, effect)`.
- 📋 Сигнатура станет свободной, параметры будут подставляться через DI (см. [Мидлвари и DI](#мидлвари-и-di)).

## Сообщения

✅ Сообщение — тоже эффект. Значит, обработчик может yield-ить сообщения. 📋 Вызвать команду или запрос и получить результат, опубликовать событие. ❓ Надо продумать семантику вложенных команд, особенно в staged-обработчиках.

| Тип | Назначение | Результат | Обработчиков на тип | Режим |
|---|---|---|---|---|
| `Command[R]` | Изменить состояние | `R` | ровно один | ephemeral или durable |
| `Query[R]` | Прочитать данные | `R` | ровно один | только ephemeral |
| `Event` | Зафиксировать факт | нет | 0..N, каждый выполняется независимо как отдельная операция | ephemeral или durable |

Объявление сообщения задаёт:

- `name` — стабильное имя для сериализации и хранения, не зависит от имени класса;
- `message_type`;
- `handler`;
- `execution_mode`.

📋 Ещё будет `version`.

✅ Объявления команд — `StagedCommandDef` и `AtomicCommandDef`. 📋 Объявления событий и запросов.

📋 `schedule(name, cron, event)` публикует событие по расписанию, `unschedule(name)` снимает его. Расписание хранится в БД.

## Обработчики сообщений

Обработчик сообщения — функция, которая возвращает генератор (`Effectful[R, E]`). Генератор yield-ит эффекты типа `E` и возвращает `R`.

**Контракт детерминизма.** Обработчик не делает ввода-вывода и не читает время, случайность и глобальное состояние напрямую — только через эффекты. При тех же входных данных и результатах эффектов он yield-ит ту же последовательность эффектов. На этом держатся ретраи, восстановление и воспроизводимость. Сейчас контракт не проверяется. 📋 По возможности ловить попытки его нарушить.

**Типы защищают от ошибок.** Тип обработчика по возможности запрещает некорректные сочетания эффектов. Например, атомарная команда не может выполнить внешнюю запись, потому что её нельзя согласовать с транзакцией БД.

### Staged

✅ `StagedHandler` yield-ит любые эффекты. Каждый эффект — отдельный шаг, у которого свой результат.

📋 События, которые yield-ит staged-обработчик, копятся в памяти и публикуются после успешного завершения операции.

📋 При сбое (ошибка или падение процесса) операция ретраится заданное число раз. Повторы безопасны, потому что ID эффектов детерминированы, а обработчики записи идемпотентны. Компенсаций нет. ❓ Возможно, позже появится отдельный вид обработчика с компенсациями.

### Atomic

📋 Выполняется в две фазы:

1. Обработчик собирает данные через `InternalEffect`, `ExternalReadEffect` и `DatabaseReadEffect`, а затем возвращает `Transaction`.
2. `Transaction` yield-ит только `DatabaseEffect` и события. Всё это выполняется в одной транзакции БД, события пишутся в outbox той же транзакцией.

❓ При ошибке транзакции обработчик ретраится целиком. Надо продумать политику ретраев.

### Query

📋 `QueryHandler` yield-ит только `ReadEffect`.

### События

📋 События доставляются через outbox: они сохраняются в БД вместе с результатом операции, а `run_outbox_dispatcher` рассылает их обработчикам. Обработка события начинается только после успешного завершения породившей его операции.

### Ошибки

- ✅ Если обработчик эффекта бросил исключение, оно пробрасывается в обработчик сообщения (`generator.throw`) в точке `yield from`. Его можно поймать в `try/except` и продолжить. Непойманное исключение завершает операцию и выходит из `Environment.execute`.
- ✅ Ошибки самого фреймворка (`UnsupportedEffectError`, `EffectNotDefinedError`, неизвестная инструкция) в обработчик не пробрасываются.
- ✅ Если выполнение прервано (отмена, закрытие плана), генератор обработчика закрывается сразу, поэтому его `finally` и `with` отрабатывают.

## Идентификаторы и детерминизм

- ✅ У каждого сообщения есть `message_id`. Его можно передать в `execute`, иначе генерируется случайный UUID (hex).
- ✅ ID эффектов детерминированно выводятся из `message_id`: генератор случайных чисел инициализируется `message_id`, и каждый следующий эффект получает следующие 16 байт в hex. Поэтому ID зависит от `message_id` и от порядкового номера эффекта.
- 📋 Всё, что порождает операция (события, вложенные сообщения), тоже получает детерминированные ID, и так далее по цепочке.
- 📋 Идемпотентность на входе: если у команды включена эта настройка, повторный вызов с тем же `message_id` возвращает сохранённый результат и не выполняет команду заново. Работает в любом режиме, не только в durable.
- 📋 Идемпотентность на выходе: `effect_id` передаётся во внешние системы как ключ идемпотентности.
- 📋 `correlation_id` и `causation_id` позволяют проследить всю цепочку сообщений в логах и трассировке.

## Режимы выполнения

Режим задаётся в объявлении сообщения (`execution_mode`).

- ✅ **Ephemeral.** Прогресс хранится только в памяти и при падении процесса теряется.
- 📋 **Durable.** Сообщение и каждый эффект (параметры и результат) записываются в БД.
  - При старте Environment подхватывает незавершённые операции.
  - Обработчик проигрывается заново на сохранённых результатах эффектов до точки остановки и продолжает выполнение.
  - ❓ Распределение работы: один универсальный тип воркера или специализированные.

📋 Команды разных режимов можно вызывать друг из друга. ❓ Надо продумать правила сочетания режимов и видов обработчиков.

## Архитектура

Как выполняется команда:

1. Вызывающий код передаёт команду в `Environment.execute`.
2. Environment получает у движка план выполнения: `OperationEngine.execute(command, message_id)`.
3. Движок запускает обработчик команды. На каждый эффект, который yield-ит обработчик, движок yield-ит инструкцию.
4. Environment исполняет инструкцию (например, вызывает обработчик эффекта) и отправляет результат в план. Движок передаёт его в обработчик команды.
5. Когда обработчик возвращает результат, план завершается, и Environment возвращает этот результат вызывающему коду.

**Движок операций** (`OperationEngine`, ✅)

- Чистый, без ввода-вывода.
- Принимает сообщение, запускает его обработчик и превращает поток эффектов в поток инструкций (`ExecutionPlan`, тоже генератор).
- Решает, как выполнять: режимы, транзакции, журнал, ретраи, публикация событий, Control-эффекты.
- Здесь сосредоточена вся сложная логика. Её проще тестировать, когда она чистая: проверяется поток инструкций без моков ввода-вывода.

**Инструкция** — команда движка для Environment.

- ✅ `CallEffectHandlerInstruction` — вызвать обработчик эффекта.
- 📋 Записать в журнал, начать или закоммитить транзакцию, записать в outbox.

**Environment** (✅)

- Исполняет инструкции и возвращает результаты в план.
- Владеет обработчиками эффектов, БД, outbox-диспетчером и планировщиком.
- Своей логики выполнения не содержит. Окружений может быть несколько (например, тестовое).

## Мидлвари и DI

📋 **Мидлвари**

- Для сообщений — чистые effectful-функции.
- Для эффектов — обычные асинхронные функции.

📋 **DI** — как в FastAPI, но без `Depends`. Зависимости связываются автоматически по типу и имени параметра, поэтому у обработчиков нет фиксированной сигнатуры.

Фабрики зависимостей:

- для эффектов — асинхронные функции или асинхронные генераторные функции (для управления жизненным циклом);
- для сообщений — effectful-функции. Для управления жизненным циклом есть специальный `ControlEffect`: через него фабрика возвращает зависимость, а её состояние сохраняется, чтобы закрыть зависимость позже.

Скоупы зависимостей: приложение, сообщение, эффект.

## Что даёт эта конструкция

Фреймворк статически знает сообщения и их обработчики, а в рантайме — каждое выполненное действие. На этом строится 📋:

- **Дашборд.**
  - Какие есть сообщения и как они выполняются.
  - Граф сообщений, построенный по типам: команда → события, которые она порождает → их события и т.д.
  - Валидация этого графа.
- **Наблюдаемость:** логи с `correlation_id`/`causation_id`, метрики и трассировка по сообщениям и эффектам — без ручной настройки.
- **Надёжность:** outbox, durable-выполнение, ретраи, идемпотентность на входе и на выходе.
- **Кеши:** движок знает, какие эффекты выполняются, поэтому сам ставит и инвалидирует кеши.
- **Тестирование:** бизнес-логика проверяется как поток эффектов, без моков.
