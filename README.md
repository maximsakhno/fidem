Фреймворк для бизнес-логики на основе системы эффектов. Обработчик сообщения — генератор: он не выполняет побочные эффекты сам, а yield-ит их описания и получает обратно результаты. Фреймворк знает каждое действие приложения, и за счёт этого даёт из коробки outbox, durable-выполнение, идемпотентность, ретраи, кеши, логи, метрики, трассировку и дашборд.

Этот документ — единый источник истины о том, как устроен фреймворк. Статусы:

- ✅ реализовано;
- 📋 запланировано;
- ❓ надо продумать.

Почему решения приняты именно так — в [записях о решениях](docs/decisions/README.md).

## Пример

```python
async def pool() -> AsyncGenerator[Pool]:
    async with create_pool(DATABASE_URL) as pool:
        yield pool


@dataclass(frozen=True, slots=True)
class GetUserEffect(DatabaseReadEffect[User]):
    user_id: str


async def handle_get_user(connection: Connection, effect: GetUserEffect) -> User: ...


@dataclass(frozen=True, slots=True)
class SaveUserEffect(DatabaseWriteEffect[User]):
    user: User


async def handle_save_user(connection: Connection, effect: SaveUserEffect) -> User: ...


@dataclass(frozen=True, slots=True)
class RenameUserCommand(Command[User]):
    user_id: str
    name: str


def rename_user(command: RenameUserCommand) -> AtomicEffectful[User]:
    user = yield from GetUserEffect(command.user_id)

    def transaction() -> TransactionEffectful[User]:
        return (yield from SaveUserEffect(replace(user, name=command.name)))

    return transaction


environment = EnvironmentImpl(
    operation_engine=OperationEngineImpl(
        command_defs=[AtomicCommandDef("rename_user", RenameUserCommand, rename_user)],
    ),
    effect_defs=[
        EffectDef(GetUserEffect, handle_get_user),
        EffectDef(SaveUserEffect, handle_save_user),
    ],
    dependency_defs=[EffectDependencyDef(pool), AsyncpgConnectionDef()],
)
async with environment:
    user = await environment.execute(RenameUserCommand("u1", "Alice"), message_id="request-42")
```

Полные примеры: [`examples/01_ephemeral_command.py`](examples/01_ephemeral_command.py), [`examples/02_dependencies.py`](examples/02_dependencies.py), [`examples/03_guards.py`](examples/03_guards.py), [`examples/04_effect_middlewares.py`](examples/04_effect_middlewares.py), [`examples/05_message_middlewares.py`](examples/05_message_middlewares.py), [`examples/06_atomic_commands.py`](examples/06_atomic_commands.py).

## Эффекты

✅ Эффект — неизменяемый объект, который описывает действие. Параметр типа — тип результата. `yield from effect` отдаёт эффект исполнителю и возвращает его результат.

Категория определяет, кто и как исполняет эффект:

| Категория        | Что это                                                                                                        | Исполняет   |
| ---------------- | -------------------------------------------------------------------------------------------------------------- | ----------- |
| `InternalEffect` | Действие внутри процесса без внешних побочных эффектов: кеш, конфиг, случайные числа, обычный `asyncio.sleep`  | Environment |
| `ExternalEffect` | Обращение к внешней системе: HTTP, брокер                                                                      | Environment |
| `DatabaseEffect` | Работа с собственной БД сервиса. Выделена отдельно, потому что на ней строятся outbox и durable-режим          | Environment |
| `ControlEffect`  | Управление выполнением: `Proceed` в [мидлвари сообщения](#мидлвари-сообщений), 📋 параллельный запуск эффектов | Движок      |

Внешние и БД-эффекты делятся на чтение и запись: `ExternalReadEffect`, `ExternalWriteEffect`, `DatabaseReadEffect`, `DatabaseWriteEffect`.

- **Чтение** можно безопасно повторять.
- **Запись** меняет состояние. Её обработчик должен быть идемпотентен по `effect_id`: при ретрае и при восстановлении операции запись повторяется с тем же ID.

### Обработчики эффектов

- ✅ Обработчик эффекта — асинхронная функция. Регистрируется в Environment через `EffectDef(effect_type, handler)`.
- ✅ На каждый тип эффекта — ровно один обработчик. Тип ищется точно, без учёта наследования.
- ✅ Сигнатура свободная: все параметры, включая сам эффект и `EffectContext`, подставляются через [DI](#di).
- ✅ Вызов обработчика оборачивается [мидлварями](#мидлвари-эффектов).

## Сообщения

✅ Сообщение — тоже эффект. Значит, обработчик может yield-ить сообщения. 📋 Вызвать команду или запрос и получить результат, опубликовать событие. ❓ Надо продумать семантику вложенных команд, особенно в staged-обработчиках.

| Тип          | Назначение         | Результат | Обработчиков на тип                                        | Режим                 |
| ------------ | ------------------ | --------- | ---------------------------------------------------------- | --------------------- |
| `Command[R]` | Изменить состояние | `R`       | ровно один                                                 | ephemeral или durable |
| `Query[R]`   | Прочитать данные   | `R`       | ровно один                                                 | только ephemeral      |
| `Event`      | Зафиксировать факт | нет       | 0..N, каждый выполняется независимо как отдельная операция | ephemeral или durable |

Объявление сообщения задаёт:

- `name` — стабильное имя для сериализации и хранения, не зависит от имени класса;
- `message_type`;
- `handler`;
- `execution_mode`.

📋 Ещё будет `version`.

✅ Объявления команд — `StagedCommandDef` и `AtomicCommandDef`. 📋 Объявления событий и запросов.

📋 `schedule(name, cron, event)` публикует событие по расписанию, `unschedule(name)` снимает его. Расписание хранится в БД.

## Обработчики сообщений

Обработчик сообщения — функция, которая возвращает генератор (`Effectful[R, E]`). Генератор yield-ит эффекты типа `E` и возвращает `R`. ✅ Сигнатура свободная: сообщение, `MessageContext` и значения [гардов](#гарды) подставляются по аннотациям.

**Контракт детерминизма.** Обработчик не делает ввода-вывода и не читает время, случайность и глобальное состояние напрямую — только через эффекты. При тех же входных данных и результатах эффектов он yield-ит ту же последовательность эффектов. На этом держатся ретраи, восстановление и воспроизводимость. Сейчас контракт не проверяется. 📋 По возможности ловить попытки его нарушить.

**Типы защищают от ошибок.** Тип обработчика по возможности запрещает некорректные сочетания эффектов. Например, atomic-обработчик может сделать только одну запись, поэтому двух несогласованных записей в нём не бывает.

### Staged

✅ `StagedHandler` yield-ит любые эффекты. Каждый эффект — отдельный шаг, у которого свой результат.

📋 События, которые yield-ит staged-обработчик, копятся в памяти и публикуются после успешного завершения операции.

✅ Ретраи после ошибки делает [мидлварь](#мидлвари-сообщений), 📋 восстановление после падения процесса — движок в [durable-режиме](#режимы-выполнения). Повторы безопасны, потому что ID эффектов детерминированы, а обработчики записи идемпотентны. Компенсаций нет. ❓ Возможно, позже появится отдельный вид обработчика с компенсациями.

### Atomic

✅ Делает ровно одну запись, поэтому проблемы двойной записи у него нет. Выполняется в две фазы:

1. Обработчик собирает данные через `InternalEffect`, `ExternalReadEffect` и `DatabaseReadEffect`, а затем возвращает одну запись: `ExternalWriteEffect` или `Transaction` — функцию без аргументов, которая возвращает генератор.
2. Запись выполняется. `ExternalWriteEffect` — как обычный эффект. `Transaction` yield-ит только `DatabaseEffect` и выполняется в одной [транзакции БД](#транзакции-бд). 📋 Ещё она yield-ит события, и они пишутся в outbox той же транзакцией.

- ✅ Обработчик аннотируется как `AtomicEffectful[R, E]`, а функция транзакции — как `TransactionEffectful[R, E]`, где `E` — события транзакции. Если транзакция не публикует событий, `E` не указывается.
- ✅ Чтения первой фазы выполняются не в транзакции записи, а каждое в своей: в первой фазе бывают медленные внешние вызовы. Согласованность чтения с записью — забота обработчика, например условие в `UPDATE`.
- ✅ Недопустимый эффект в любой фазе — ошибка фреймворка `UnsupportedEffectError`, другой результат обработчика — `UnsupportedAtomicResultError`.
- ✅ ID эффектов записи продолжают последовательность чтений, как если бы обработчик yield-ил их сам.
- ✅ Ошибка эффекта транзакции пробрасывается в генератор транзакции. Непойманная ошибка или ошибка коммита откатывает транзакцию и выходит из `Proceed` и `Environment.execute`.

📋 Несколько записей в разные системы согласуются по паттерну transactional outbox: операция пишет в свою БД и в той же транзакции публикует события, а во внешние системы пишут обработчики этих событий.

📋 Выполняется только в ephemeral-режиме: запись одна, восстанавливать после падения нечего.

❓ При ошибке транзакции обработчик ретраится целиком. Надо продумать политику ретраев и нужен ли ретрай одной транзакции без первой фазы.

### Query

📋 `QueryHandler` yield-ит только `ReadEffect`.

### События

📋 События доставляются через outbox: они сохраняются в БД вместе с результатом операции, а `run_outbox_dispatcher` рассылает их обработчикам. Обработка события начинается только после успешного завершения породившей его операции.

### Ошибки

- ✅ Если обработчик эффекта бросил исключение, оно пробрасывается в обработчик сообщения (`generator.throw`) в точке `yield from`. Его можно поймать в `try/except` и продолжить. Непойманное исключение завершает операцию и выходит из `Environment.execute`.
- ✅ Ошибки самого фреймворка (`UnsupportedEffectError`, `UnsupportedAtomicResultError`, `EffectNotDefinedError`, неизвестная инструкция) в обработчик не пробрасываются.
- ✅ Если выполнение прервано (отмена, закрытие плана), генератор обработчика закрывается сразу, поэтому его `finally` и `with` отрабатывают.

## Идентификаторы и детерминизм

- ✅ У каждого сообщения есть `message_id`. Его можно передать в `Environment.execute`, иначе Environment генерирует случайный UUID (hex). `MessageContext` создаёт только Environment и передаёт его в движок, поэтому у сообщения один контекст.
- ✅ ID эффектов детерминированно выводятся из `message_id`: генератор случайных чисел инициализируется `message_id` с префиксом его длины, и каждый следующий эффект получает следующие 16 байт в hex. Поэтому ID зависит от `message_id` и от порядкового номера эффекта. Префикс длины не даёт сидам разных сообщений совпасть.
- ✅ У каждого [гарда](#гарды) и каждой [мидлвари сообщения](#мидлвари-сообщений) свой такой генератор. У мидлвари к сиду сообщения добавляется `#middleware:` и её имя, а сиды гардов начинаются с `:`, поэтому не совпадают с ними. У гарда к сиду сообщения добавляются имя гарда из `GuardDef` и `module.qualname` типа его значения. Поэтому добавление или изменение гарда или мидлвари не сдвигает ID эффектов обработчика. `module` зависит от точки входа: у модуля, запущенного скриптом, это `__main__`, так что ID эффектов гардов из него меняются при импорте.
- 📋 Всё, что порождает операция (события, вложенные сообщения), тоже получает детерминированные ID, и так далее по цепочке.
- 📋 Идемпотентность на входе: если у команды включена эта настройка, повторный вызов с тем же `message_id` возвращает сохранённый результат и не выполняет команду заново. Работает в любом режиме, не только в durable.
- 📋 Идемпотентность на выходе: `effect_id` передаётся во внешние системы как ключ идемпотентности.
- 📋 `correlation_id` и `causation_id` позволяют проследить всю цепочку сообщений в логах и трассировке.

## Режимы выполнения

Режим задаётся в объявлении сообщения (`execution_mode`).

- ✅ **Ephemeral.** Прогресс хранится только в памяти и при падении процесса теряется.
- 📋 **Durable.** Сообщение и каждый эффект (параметры и результат) записываются в журнал операции в БД. Журнал один на всю цепочку, у каждой записи указан источник: гард, мидлварь или обработчик.
  - При старте Environment подхватывает незавершённые операции.
  - Вся цепочка, включая гарды, проигрывается заново на сохранённых результатах эффектов до точки остановки и продолжает выполнение. Поэтому значения гардов сериализовать не нужно.
  - `Proceed` — тоже шаг журнала, у каждой попытки внутренней части свой раздел.
  - Журнал копится в памяти и сбрасывается в БД перед первой записью.
  - В журнале сохраняется состав цепочки с именами и версиями мидлварей, чтобы восстановление шло тем же кодом.
  - ❓ Распределение работы: один универсальный тип воркера или специализированные.

📋 Команды разных режимов можно вызывать друг из друга. ❓ Надо продумать правила сочетания режимов и видов обработчиков.

## Архитектура

Как выполняется команда:

1. Вызывающий код передаёт команду в `Environment.execute`.
2. Environment получает у движка план выполнения: `OperationEngine.execute(command, message_context)`.
3. Движок запускает обработчик команды. На каждый эффект, который yield-ит обработчик, движок yield-ит инструкцию.
4. Environment исполняет инструкцию (например, вызывает обработчик эффекта) и отправляет результат в план. Движок передаёт его в обработчик команды.
5. Когда обработчик возвращает результат, план завершается, и Environment возвращает этот результат вызывающему коду.

**Движок операций** (`OperationEngine`, ✅)

- Чистый, без ввода-вывода.
- Принимает сообщение, запускает его обработчик и превращает поток эффектов в поток инструкций (`ExecutionPlan`, тоже генератор).
- Решает, как выполнять: режимы, транзакции, журнал, ретраи, публикация событий, Control-эффекты.
- Здесь сосредоточена вся сложная логика. Её проще тестировать, когда она чистая: проверяется поток инструкций без моков ввода-вывода.

**Инструкция** — команда движка для Environment.

- ✅ `CallEffectHandlerInstruction` — вызвать обработчик эффекта. Содержит эффект, `EffectContext`, а также сообщение и `MessageContext`, которые его породили.
- ✅ `RunTransactionInstruction` — выполнить вложенный план инструкций в одной [транзакции БД](#транзакции-бд) и вернуть его результат.
- 📋 Записать в журнал, записать в outbox.

**Environment** (✅)

- Исполняет инструкции и возвращает результаты в план.
- Запускается и останавливается через `async with environment:`, `execute` вне этого блока — ошибка.
- На старте создаёт APPLICATION-зависимости эффектов, на остановке закрывает их.
- Владеет обработчиками эффектов, БД, outbox-диспетчером и планировщиком.
- Своей логики выполнения не содержит. Окружений может быть несколько (например, тестовое).

## Мидлвари

### Мидлвари эффектов

✅ Мидлварь (`EffectMiddleware`) — асинхронная функция `middleware(effect_call, call_next)`. `EffectCall` содержит сообщение, `MessageContext`, эффект и `EffectContext` из инструкции движка. `call_next()` без аргументов вызывает следующую мидлварь, а после последней — обработчик эффекта. Подменить эффект или контекст нельзя: мидлварь их только читает.

- Мидлвари срабатывают до [DI](#di). Последний `call_next` создаёт EFFECT-скоуп, резолвит зависимости, вызывает обработчик эффекта и закрывает скоуп. Эффекту БД вне транзакции он сначала создаёт [неявную транзакцию](#транзакции-бд). Поэтому:
  - каждый вызов `call_next` получает новые EFFECT-зависимости и новую неявную транзакцию, а MESSAGE-зависимости создаются один раз на сообщение и при повторном вызове не пересоздаются;
  - ошибки резолва и закрытия мидлварь видит как ошибки `call_next`.
- Мидлварь может не вызвать `call_next` (кеш, заглушка) или вызвать несколько раз (ретрай), в том числе одновременно: MESSAGE-зависимость всё равно создаётся один раз.
- `call_next` после завершения сообщения — ошибка `ScopeClosedError`. Созданная при этом MESSAGE-зависимость сразу закрывается.
- Мидлварь — только `async def`-функция, иначе ошибка `UnsupportedFunctionError` при создании Environment.
- Мидлвари регистрируются через `EffectMiddlewareDef(middleware)`. Общий список — `EnvironmentImpl(effect_middleware_defs=...)`. Список в `EffectDef(..., middleware_defs=...)` заменяет общий для этого эффекта, `()` — без мидлварей. Первая в списке — внешняя.
- Список мидлварей каждого эффекта собирается один раз при создании Environment.
- Ошибка мидлвари — ошибка эффекта, она пробрасывается в обработчик сообщения. `EffectNotDefinedError` возникает до мидлварей.
- Через мидлвари проходят все эффекты, в том числе эффекты гардов и мидлварей сообщений.
- Зависимости мидлварь получает только через замыкание. ❓ Доступ мидлварей к APPLICATION-зависимостям эффектов.

### Мидлвари сообщений

✅ Мидлварь сообщения (`MessageMiddleware`) оборачивает обработчик сообщения. Это генераторная функция, как и обработчик: она yield-ит эффекты и возвращает результат операции. `yield from Proceed()` выполняет внутреннюю часть цепочки (следующую мидлварь, а после последней — обработчик) и возвращает её результат. Эффекты внутренней части мидлварь не видит и подменить не может, поэтому не нарушит гарантии обработчика, например атомарность. Подменить можно только результат.

- Сигнатура свободная: сообщение, `MessageContext` и значения [гардов](#гарды) подставляются по аннотациям, как у обработчика.
- Сначала выполняются гарды обработчика и всех его мидлварей, потом мидлвари, потом обработчик. Поэтому общая мидлварь, например кеш, не обходит проверку прав.
- Мидлварь yield-ит любые эффекты, кроме сообщений и чужих control-эффектов, в том числе запись: кешу нужно сохранить результат. `Proceed` вне мидлвари — ошибка `UnsupportedEffectError`.
- Мидлварь может не вызвать `Proceed` (кеш) или вызвать несколько раз (ретрай). Каждый вызов запускает внутреннюю часть заново, и её эффекты получают те же [ID](#идентификаторы-и-детерминизм). Гарды при этом не перезапускаются.
- Ошибка внутренней части пробрасывается в мидлварь в точке `yield from Proceed()`, её можно поймать. [Ошибки фреймворка](#ошибки), которые не пробрасываются в обработчик, не пробрасываются и в мидлварь. При прерывании закрываются все генераторы цепочки.
- Мидлварь регистрируется через `MessageMiddlewareDef(name, middleware)`. Имя стабильное: от него зависят ID эффектов мидлвари. Одинаковые имена в одном списке — ошибка `DuplicateMessageMiddlewareDefError`.
- Общий список — `OperationEngineImpl(middleware_defs=...)`. Список в `StagedCommandDef(..., middleware_defs=...)` заменяет общий для этой команды, `()` — без мидлварей. Первая в списке — внешняя.
- Мидлвари и их гарды проверяются при создании движка для всех команд, в том числе atomic. У atomic-команды `Proceed` выполняет обе фазы и возвращает результат записи.
- Настройки мидлварь получает через замыкание.

**Ограничения:** мидлварь — только синхронная генераторная функция, иначе ошибка `UnsupportedFunctionError` при создании движка.

## DI

✅ Каждый параметр обработчика эффекта или фабрики — зависимость, и связываются они автоматически, без явных маркеров. Поэтому фиксированной сигнатуры нет ни у обработчиков, ни у фабрик. Зависимости — инфраструктура: подключение к БД, клиент внешнего сервиса. Регистрируются в `EnvironmentImpl(dependency_defs=...)`.

### Принципы

- **Всё готовится заранее.** При создании Environment и движка граф зависимостей строится и проверяется целиком: каждому параметру есть зависимость, выбор однозначен, циклов нет, скоупы соблюдены. Проверяются и зависимости, которые пока не нужны ни одному обработчику. Для каждого обработчика заранее готовится порядок резолва, поэтому во время обработки сообщения ничего не выясняется — подготовленные шаги просто выполняются.
- **Резолв отделён от вызова.** Сначала резолвятся зависимости, потом обработчик вызывается с готовыми зависимостями. Поэтому стратегию резолва можно менять, не трогая вызов.
- **Скоупы вложены.** Зависимость может зависеть только от зависимостей с таким же или более широким скоупом.
- **Сначала по типу, потом по имени.** Ключ зависимости — тип и необязательное имя.
  1. Кандидаты — зависимости, тип которых совпадает с типом параметра или наследует его. Точное совпадение не приоритетнее наследника.
  2. Если кандидат один, берём его, имя не важно.
  3. Если кандидатов несколько, берём того, чьё имя совпадает с именем параметра.
  4. Иначе ошибка: зависимость не найдена или выбор неоднозначен.

  Generic-тип (`Repo[User]`) совпадает только точно, но `C[Any]` равен `C`.

✅ **Фабрика** — асинхронная генераторная функция. Код до `yield` создаёт зависимость, значение `yield` — сама зависимость, код после `yield` закрывает её при выходе из скоупа. Генератор получает в точке `yield` ошибку, с которой завершился скоуп, и может, например, откатить транзакцию вместо коммита. Фабрика регистрируется через `EffectDependencyDef(factory, lifetime=...)`.

✅ **Скоупы** задают время жизни зависимости:

| Скоуп         | Время жизни                                    | Когда создаётся                                                                                                                                      |
| ------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `APPLICATION` | работа Environment (`async with environment:`) | на старте, параллельно: каждая зависимость — как только готовы те, от которых она зависит. Закрываются тоже параллельно, по графу в обратную сторону |
| `MESSAGE`     | обработка одного сообщения                     | лениво, при первом эффекте, которому она нужна                                                                                                       |
| `TRANSACTION` | одна [транзакция БД](#транзакции-бд)           | лениво, при первом эффекте транзакции, которому она нужна                                                                                            |
| `EFFECT`      | один вызов обработчика эффекта                 | перед вызовом                                                                                                                                        |

- Зависимости `MESSAGE`, `TRANSACTION` и `EFFECT` резолвятся последовательно, по заранее отсортированному списку: задачи asyncio на каждом эффекте снизили бы производительность. ❓ Возможно, позже можно будет выбирать последовательный или параллельный резолв.

✅ **Встроенные зависимости** — сообщение, `MessageContext`, `TransactionContext`, эффект и `EffectContext`. Они лежат в скоупах наравне с остальными и сопоставляются по общим правилам, поэтому фабрика может получить эффект по базовому классу (`Effect[Any]`). Исключение — сообщение: какое сообщение породит эффект, заранее неизвестно. Поэтому сообщение подходит только параметру типа `Message` или его подкласса, а подкласс проверяется в рантайме.

✅ **Ошибки**

- Если резолв упал, уже созданные зависимости закрываются.
- Закрываются все созданные зависимости, даже если какая-то упала при закрытии.
- Если упало закрытие EFFECT-зависимости, эффект считается упавшим: ошибка уходит в обработчик сообщения как ошибка эффекта.
- Отмена и прерывание не заворачиваются в группу ошибок, иначе asyncio не распознает отмену.

**Ограничения**

- Обработчики — только `async def`-функции. Параметры у них и у фабрик аннотированы и передаются по имени.
- ❓ Не защищены одновременные старты Environment и вызовы `execute` во время остановки.

**Почему так**

- **Один вид фабрики.** Генератор покрывает все случаи: зависимость без кода закрытия он отдаёт через `yield` и завершается. 📋 Готовый объект и асинхронную функцию сведут к генераторной хелперы вне ядра.
- **Цена генератора.** Генератор без кода закрытия резолвится примерно за 0,9 мкс против 0,06 мкс у асинхронной функции. На фоне I/O обработчиков эффектов разница незаметна. Если станет мешать, ядро сможет вызывать функцию из хелпера напрямую, не меняя API.

## Транзакции БД

✅ Ядро не привязано к БД, драйверу и ORM. Транзакция — это скоуп DI `TRANSACTION`, а begin, commit и rollback делает фабрика этого скоупа: она видит ошибку, с которой скоуп завершился. Обработчик эффекта получает от фабрики объект драйвера как есть, например `asyncpg.Connection`. В той же транзакции можно построить и свои зависимости, например сессию ORM или репозитории.

```python
async def connection(pool: Pool) -> AsyncGenerator[Connection]:
    async with pool.acquire() as connection, connection.transaction():
        yield connection


dependency_defs = [EffectDependencyDef(connection, lifetime=EffectDependencyLifetime.TRANSACTION)]
```

- **Явная транзакция** — `Transaction` [atomic-команды](#atomic). Движок yield-ит `RunTransactionInstruction`, Environment открывает скоуп, выполняет вложенный план и закрывает скоуп с ошибкой, с которой тот завершился. Поэтому транзакция откатывается и при ошибке, и при отмене. Ошибка коммита возвращается в план как ошибка инструкции.
- **Неявная транзакция** — у `DatabaseEffect` вне явной: скоуп на один вызов обработчика, внутри последнего `call_next` [мидлварей эффекта](#мидлвари-эффектов). Поэтому ретрай мидлварью получает новую транзакцию. Ошибка закрытия скоупа — ошибка эффекта.
- Транзакция без эффектов, которым нужны её зависимости, соединение не берёт.
- `TransactionContext(read_only)` — встроенная зависимость скоупа. `read_only` истинно у неявной транзакции вокруг `DatabaseReadEffect`, и фабрика может не открывать для неё транзакцию БД: при read committed каждый запрос и так видит свой снимок.
- Зависимости скоупа `TRANSACTION`, в том числе `TransactionContext`, доступны только обработчикам `DatabaseEffect`, напрямую или через `EFFECT`-зависимости. Иначе ошибка `TransactionDependencyAccessError` при создании Environment. Пул соединений — обычная зависимость, его так не ограничить.
- Вложенная транзакция — ошибка `NotImplementedError`: она взяла бы другое соединение.

**Ограничения:** ретрай отдельного эффекта мидлварью эффекта внутри явной транзакции повторяет его в той же транзакции, а в PostgreSQL транзакция после ошибки запроса уже сломана. Ретраить надо команду целиком, мидлварью сообщения. ❓ Savepoint-ы. ❓ Где открывать неявную транзакцию в durable-режиме, чтобы запись эффекта и запись журнала шли одной транзакцией.

### asyncpg

✅ `fidem[asyncpg]` ставит фреймворк с asyncpg. `AsyncpgConnectionDef` объявляет зависимость `asyncpg.Connection` скоупа `TRANSACTION`: соединение берётся из зависимости `asyncpg.Pool` и работает в транзакции с настройками `AsyncpgTransactionOptions`, пока это только уровень изоляции. Пул приложение объявляет своей фабрикой: она зависит от его настроек.

```python
AsyncpgConnectionDef(
    options=AsyncpgTransactionOptions(isolation="read_committed"),
    message_options={TransferCommand: AsyncpgTransactionOptions(isolation="serializable")},
)
```

- `options` — настройки по умолчанию, `message_options` — настройки транзакций сообщения, тип которого совпадает точно. Настройки драйвера живут в его объявлении, а не в объявлении команды: ядро о них не знает.
- Настройки сообщения действуют во всех его транзакциях, кроме неявных транзакций чтения: такая транзакция обёрнута вокруг одного чтения, а настройки сообщения нужны его записям.
- Неявная транзакция чтения при read committed не открывается.
- Транзакцию фабрика открывает и коммитит SQL-командами. Коммит транзакции, в которой упал запрос, PostgreSQL молча превращает в откат. Тогда фабрика бросает `TransactionRolledBackError`, а не сообщает об успехе. `Connection.transaction()` asyncpg этого не замечает.

**Ограничения:** внутри транзакции фабрики обработчик не может вызвать `connection.transaction()`, asyncpg запрещает его в транзакции, открытой SQL-командой. Savepoint — SQL-командой.

Из пула под типом `Connection` приходит `PoolConnectionProxy`: он передаёт всё соединению, и asyncpg описывает его как соединение.

## Гарды

✅ Гард аутентифицирует отправителя сообщения или проверяет его права. Это генераторная функция: она yield-ит эффекты и возвращает значение через `return`, а обработчик получает это значение параметром. Тип значения — первый параметр аннотации `Effectful[ValueT, GuardEffect]`. Гард регистрируется через `GuardDef(guard)` в `OperationEngineImpl(guard_defs=...)`.

- ✅ Сигнатура свободная: параметры — сообщение, `MessageContext` и значения других гардов. Они сопоставляются по [принципам DI](#принципы), скоупов нет. Гарды и зависимости эффектов не пересекаются.
- ✅ Проверка прав выражается типом значения: гард `admin(user: CurrentUser) -> Admin` либо возвращает `Admin`, либо бросает исключение, поэтому обработчик с параметром `admin: Admin` выполняется только для админа. В отличие от гардов NestJS и Litestar, которые только пропускают или отклоняют, гард возвращает значение.
- ✅ Гарды, нужные обработчику и его [мидлварям](#мидлвари-сообщений), выполняются перед ними на каждое сообщение, каждый один раз и после гардов, от которых зависит.
- ✅ Гард yield-ит только чтение (`ExternalReadEffect`, `DatabaseReadEffect`) и `InternalEffect`. Статически это задаёт аннотация `GuardEffect`, в рантайме проверяет движок. 📋 Запросы (`Query`).
- ✅ Настройки и общие объекты, например проверку токенов, гард получает через замыкание.
- 📋 У каждой операции свои значения гардов: вложенная команда и каждый обработчик события не наследуют значения родительской операции.

✅ **Встроенные значения** — сообщение и `MessageContext`. Тип сообщения у обработчика известен заранее, поэтому сообщение сопоставляется по общим правилам, в том числе по базовому классу. Если гарду нужен тип сообщения, отличный от сообщения обработчика, это ошибка при создании движка.

✅ **Ошибки**

- Ошибка эффекта пробрасывается в гард в точке `yield from`, как в обработчик.
- Если гард упал, обработчик не вызывается, ошибка выходит из `Environment.execute`.
- Недопустимый эффект — ошибка фреймворка (`UnsupportedEffectError`), в гард она не пробрасывается.

**Ограничения:** обработчики сообщений и гарды — только синхронные генераторные функции, иначе нарушится детерминизм. Параметры у них аннотированы и передаются по имени.

**Почему так**

- **Узкое назначение.** Других применений DI сообщений, кроме аутентификации и проверки прав, не нашлось: инфраструктура и ресурсы — в зависимостях эффектов, сквозная логика — в мидлварях. Поэтому механизм заточен под эту задачу.
- **Без скоупов и частных видов.** В ядре один вид гарда — генераторная функция. Общий для всех сообщений объект передаётся через замыкание. 📋 Частные случаи, например обычную функцию, сведут к генераторной хелперы вне ядра.
- **Без кода закрытия.** Рассматривали гард, который отдаёт значение через `ControlEffect` и после него закрывает его. Отказались: ресурсов у гардов нет, а закрытие усложняет durable-режим и отмену (при закрытии генератора yield-ить эффекты нельзя). С `return` правило «ровно одно значение» гарантирует язык, а не проверка в рантайме.
- **Только чтение.** Чтение безопасно повторять, поэтому гарды можно проигрывать заново при восстановлении. Ограничение одинаково для всех видов обработчиков, в том числе для atomic и query.

## Что даёт эта конструкция

Фреймворк статически знает сообщения и их обработчики, а в рантайме — каждое выполненное действие. На этом строится 📋:

- **Дашборд.**
  - Какие есть сообщения и как они выполняются.
  - Граф сообщений, построенный по типам: команда → события, которые она порождает → их события и т.д.
  - Валидация этого графа.
- **Наблюдаемость:** логи с `correlation_id`/`causation_id`, метрики и трассировка по сообщениям и эффектам — без ручной настройки.
- **Надёжность:** outbox, durable-выполнение, ретраи, идемпотентность на входе и на выходе.
- **Кеши:** движок знает, какие эффекты выполняются, поэтому сам ставит и инвалидирует кеши.
- **Тестирование:** бизнес-логика проверяется как поток эффектов, без моков.
